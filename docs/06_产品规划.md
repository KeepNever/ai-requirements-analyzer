## 1. 版本切分总览

| 版本 | 定位 | 核心命题 | 状态 |
|---|---|---|---|
| V0 原型 | Prompt 试金石 | 8 节点 Prompt 方向对不对？ | 未开始 |
| **V1 MVP** | 本项目主体 | 分析结果比人工总结更有价值，且可信可测 | 进行中（文档阶段） |
| V1.5 | 有限自主 | 动态轮次 + 批评家对照实验 | 规划 |
| V2 | 产品纵深 | 多轮演化 / RAG / Agent 化 / 状态复核 | 规划 |

> **V1 核心验证目标：** 验证 AI 能否在典型 B 端 SaaS 客户需求材料场景下，相比人工整理，更快、更完整、更可追溯地形成结构化需求分析结果，并通过测试集与人工标准验证其可靠性。
>
> **成功标准不是 Workflow 节点数量、页面数量或 Agent 化程度，而是核心分析质量是否达到预设标准。**

### 2.2 V1 明确不做（Out）

| 排除项 | 原因 | 去向 |
|---|---|---|
| Agent 自主规划/动态循环 | 固定流程可测试可兜底，自主性按需分配 | V1.5/V2 |

| 自动学习/模型更新 | 修正数据只做 Badcase 归档与 Prompt 优化 | V2+ |
| 真实客户数据接入 | 合规红线，Demo 全程虚构数据 | 不做 |

## 3. 里程碑计划

| 里程碑 | 交付物 | 验收标准 |
|---|---|---|
| M0 文档阶段 ✅ | 01~07 号文档 | 需求定义/框架/测试集齐备，GT 可用 |
| M1 单案例跑通 | 最小 Workflow 代码 + CASE-01 全链路输出 | 9 字段报告生成，引用校验通过，人工通读无硬伤 |
| M2 首轮评测 | 5 案例批量评测 + 评测报告 v1 | 四核心指标出数，Badcase 清单成型 |
| M3 迭代验证 | 基于 M2 Badcase 的必要 Prompt 优化（不固定轮次）+ 每轮指标记录 + 批评家对照实验 | 核心指标较 M2 明确改善，**或能明确定位当前模型能力边界**；批评家去留必须有实验数据依据 |
| M4 前端 Demo | 报告页 + 修正留痕 + 状态流转 + 三角色视图 | 可演示完整用户旅程 |
| M5 产品验收 | 评测报告终版 + 核心功能稳定 | 关键指标与 Badcase 可复现 |

### 3.1 作品集交付标准（独立于产品验收）

- GitHub 仓库结构完整，commit 历史能体现主要迭代过程
- 项目背景、问题、方案、评测、迭代、最终结果形成完整案例
- 可现场演示从客户材料输入到需求分析报告输出的完整链路

> 节奏原则：M1 用最便宜的路径跑通（单文件脚本即可，不搭框架）；M2 之前不写任何前端；每轮迭代 commit 带评测轮次与指标变化。

## 5. 风险登记表

| 风险 | 概率 | 应对 |
|---|---|---|
| 分析质量不达 GT 期望 | 中 | 正常现象——Badcase 驱动 Prompt 迭代正是方法论本身；M2 只求出数不求好看 |
| 评分人一致率 < 80% | 中 | 先修 GT 模糊条目再修 Prompt；分歧案例单独归档 |
| 范围蔓延（做文档时想加功能） | 高 | 本文档 In/Out 表为唯一依据，新增功能一律进 V1.5/V2 清单 |
| 单人评分精力不足 | 中 | 最低配置：另一模型盲评修订 + 自我隔时复评，如实记录方法局限 |
| API 成本失控 | 低 | 已核算全流程 3~5 元；免费裁判 + 低价主力 |
