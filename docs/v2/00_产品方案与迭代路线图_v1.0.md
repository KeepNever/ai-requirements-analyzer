# AI 客户材料分析工作台：产品方案与迭代路线图

> 文档版本：v1.0 方案草案  
> 日期：2026-10-20  
> 项目基础：AI 客户需求分析助手（现有 Web Demo）  
> 本文用途：统一产品定位、用户流程、功能范围、知识库问答设计、技术边界、评测方法与迭代顺序，供后续产品决策、原型设计和 Codex/WorkBuddy 实施使用。

## 0. 一页摘要

### 0.1 产品定位

建议将现有「AI 客户需求分析助手」逐步发展为一个 **面向 B 端售前、产品经理和解决方案人员的 AI 客户材料分析工作台**。

它不是只提供文件上传和聊天的普通知识库，也不是只生成一次性需求报告的分析脚本，而是让用户围绕一个客户项目完成以下工作：

1. 收集会议纪要、微信记录、邮件、访谈笔记等客户材料；
2. 清洗材料，并保留清洗文本与原文段落之间的映射；
3. 针对当前项目的材料进行 AI 知识问答，答案能够追溯至原文；
4. 从材料中识别显性需求、潜在需求、待确认事项和业务约束；
5. 生成需求分析、优先级建议、能力匹配与后续追问；
6. 让用户核实、修正和确认 AI 结论，并将确认结果沉淀到项目报告；
7. 导出可以交付或继续跟进的分析报告。

产品的核心价值是：**从分散客户材料中找出可核实的信息，帮助用户形成需求判断，并明确哪些结论有依据、哪些信息仍需确认、下一步应该问什么。**

### 0.2 产品体验主线

建议采用「项目工作台 + 资料库 + AI 对话 + 需求分析 + 证据审查」的结构。AI 对话不是孤立的聊天页，而是整个工作流程中的交互入口：用户可以问问题、查看原文、把回答转成需求、生成追问，或跳转到正式分析报告。

### 0.3 建设顺序

| 阶段 | 重点 | 主要交付 | 是否改变现有 Prompt |
|---|---|---|---|
| P0 | 数据与证据基础 | 文件/清洗文本/原文段落 ID 的映射、索引数据结构、项目数据隔离 | 否 |
| P1 | 清洗后资料库 + AI 知识问答 | 上传、清洗预览、建立索引、带引用问答、原文跳转、问答历史 | 否，独立新增问答链路 |
| P2 | 与需求分析闭环 | 从问答转需求、生成追问、合并进分析报告、人工确认与修正 | 现有分析 Prompt 先冻结 |
| P3 | 引用覆盖自检 + 报告交付 | 引用完整性检查、缺失事实点提示、Word/PDF 导出 | 优先用程序和现有指标做校验，不先改现有 Prompt |
| P4 | 增强能力 | 多文件批处理、跨项目比较、多人协作、复杂检索等 | 另行立项与评测 |

**第一版不追求功能多，而是跑通「上传资料 → 清洗并确认 → 对资料提问 → 点开引用核实 → 将结论进入需求分析 → 形成报告」这条完整链路。**

## 1. 项目背景与当前基础

### 1.1 当前已具备的能力

根据现有项目记录，当前 Web Demo 已具备以下基础能力：

- 基于 `python web_demo.py` 启动的 Web 工作台；
- 粘贴原始材料，进行清洗预览；
- 一键调用 DeepSeek 进行真实分析；
- 以分节点方式查看分析流水线；
- 生成结构化分析报告，展示雷达图、优先级矩阵、能力匹配分布等；
- 评测 Dashboard 与离线评测流程；
- Python 标准库 Web、JSON Schema 逐级校验及 pytest 测试；
- 现有分析流程采用固定 Workflow，强调可检查、可评测和可追溯。

现役冻结基线记录为：

| 项目 | 基线 |
|---|---|
| Prompt | v1.7.1 |
| 评测器 | metrics v1.5 |
| validation GT | v1.1 |
| final GT | v1.0 |
| Git 标签 | `m4-freeze` |
| 自动化测试 | 28 项全绿（以现有决策报告记录为准） |

### 1.2 当前能力评测概况

以下数值来自现有项目报告，作为当前分析链路的历史基线，并非新增知识库问答功能的测试结果。

| 指标 | MAIN | DEV | HOLD | FINAL | 现阶段解读 |
|---|---:|---:|---:|---:|---|
| ① 需求提取 F1 | 0.698 | 0.831 | 0.797 | 0.789 | 提取表现处于相近区间，但仍需结合案例理解 |
| ② 关键需求遗漏率 | 0.067 | 0.250 | 0.167 | 0.000 | FINAL 六案关键需求全部命中；小样本不代表普遍有效 |
| ③ 引用错位嫌疑 | 0.308 | 0.139 | 0.056 | 0.304 | 复杂、矛盾或跑题材料下需继续检查引用质量 |
| ⑤ 优先级一致率 | 0.717 | 0.622 | 0.750 | 0.397 | 已知弱项，曾出现单向向上跳档；目前挂账，不在本轮强行修复 |
| ⑥ 能力匹配一致率 | 0.683 | 0.767 | 0.861 | 0.606 | 新案例上的边界理解仍有分歧 |
| ⑦ 引用完整率 | 0.420 | 0.711 | 0.500 | 0.339 | 多条需求只引用了主要出处，遗漏次级事实点 |

注意：⑦另有连续覆盖均值口径，不能与「完整率」混用。建议后续报告始终同时注明指标名称、计算口径、数据集身份和样本量。

### 1.3 为什么扩展产品形态

当前系统已有清洗、需求分析、报告和评测基础。如果仅继续改 Prompt，容易将项目长期限制在「不断调分析结果」上；而用户实际工作的前后环节还有信息检索、跨材料问答、核实出处、持续补充信息和交付报告等需求。

因此，新阶段不应推倒现有分析链路，而应在冻结的分析能力外层增加一个面向用户的工作台，将资料、问答、分析与人工确认连接起来。新增知识问答功能应独立开发、独立测试，不和当前优先级评分问题混成同一轮实验。

## 2. 产品目标、用户与使用场景

### 2.1 产品目标

**核心目标：** 帮助 B 端业务人员把零散的客户沟通材料转化为可检索、可引用、可判断、可跟进的需求信息。

具体目标：

1. 降低从多份材料中寻找客户信息的时间；
2. 回答必须尽可能有原文证据，不把模型推断包装成事实；
3. 保留材料清洗、需求抽取、分析判断之间的来源映射；
4. 让 AI 对话结果能进入正式需求分析，而不是只停留在聊天记录里；
5. 支持人工确认和修正，并记录关键修改原因；
6. 让产品能通过固定测试集验证功能变化，而非只凭演示感觉判断质量。

### 2.2 首要用户

| 用户 | 典型任务 | 当前痛点 | 产品提供的价值 |
|---|---|---|---|
| 售前顾问/解决方案人员 | 读会议纪要、提炼客户场景、核对产品能否满足 | 材料分散、需求不清楚、方案前提易遗漏 | 多文件问答、能力匹配依据、缺口和追问清单 |
| B 端产品经理 | 区分事实、推断与待确认信息，整理需求和优先级 | 需手动对照原文、风险点容易遗漏 | 需求分析草稿、引用跳转、人工修正、待确认状态 |
| 销售/客户成功 | 查找客户说过什么、准备下一轮沟通 | 搜索效率低、容易凭印象回复 | 以项目资料为范围的问答和沟通问题建议 |

V1 不追求为三个角色建设完整权限系统。首期可通过页面入口和功能范围区分常见工作任务，但项目与文件的访问隔离必须在服务层落实，不能只靠前端隐藏按钮。

### 2.3 典型使用场景

**场景 A：找事实**

用户问「客户有没有明确说数据不能出内网？」系统检索项目资料，回答是否存在明确表述，提供文件名、段落编号和原文摘录。若不同材料说法不一致，应并列展示，不代替用户裁定。

**场景 B：跨文件问答**

用户上传会议纪要、后续邮件和微信记录，问「客户对上线时间的说法有没有变化？」系统按时间与来源列出相关证据，并指出一致部分和冲突部分。

**场景 C：整理需求**

用户问「把客户关于自动预警的要求整理出来」。系统提取需求候选，列出原文依据、涉及对象、业务目的和未确认事项；用户确认后，才将其写入正式需求清单。

**场景 D：准备追问**

用户问「下一次会议还要确认什么？」系统根据材料中的缺口、矛盾和产品能力边界生成具体问题，并说明每个问题为什么需要问。

**场景 E：形成交付物**

完成材料分析后，用户查看需求列表、关键缺口、能力匹配和引用证据，再导出报告给内部团队评审或准备客户沟通。

## 3. 产品定位与差异化

### 3.1 不做“只会聊天的知识库”

普通知识库问答通常解决「资料里有什么」。本项目还要回答：

- 这段内容是客户明确说的事实，还是根据上下文推断的可能需求？
- 哪些内容是需求，哪些只是诉求、背景或闲聊？
- 哪些需求当前证据不足，应该列为待确认？
- 哪些信息在不同材料里相互矛盾？
- 需求与产品能力是否匹配，判断依据是什么？
- 哪些重要事实点没有被引用？
- 下一轮应该追问客户什么？

### 3.2 差异化主张

建议围绕四个产品差异化点展开：

1. **证据优先：** 每个重要结论尽量能定位到原文，不要求用户无条件相信模型；
2. **事实与判断分层：** 明确区分客户原话、模型推断、待确认信息；
3. **分析闭环：** 从问答到需求清单、从需求清单到追问和报告，避免各模块彼此割裂；
4. **可验证：** 使用固定 GT、回归集和质量指标跟踪变化，诚实记录失败案例。

### 3.3 产品名称建议

- 项目/代码仓库名称继续沿用：`AI 客户需求分析助手`；
- Web 产品展示名可使用：**AI 客户材料分析工作台**；
- 副标题：**把客户材料变成可追溯的需求判断与下一步行动。**

这样能够在保留现有项目资产的同时，说明产品形态已经从单次分析助手扩展为工作台。

## 4. 产品信息架构与页面设计

### 4.1 一级导航

建议使用以下信息架构：

1. **项目首页**：最近项目、最近处理材料、分析进度、待确认事项；
2. **资料库**：项目文件列表、清洗预览、索引状态、版本管理；
3. **AI 问答**：针对当前项目或选中文件提问，回答带引用；
4. **需求分析**：显性需求、潜在需求、待确认信息、优先级与能力匹配；
5. **证据审查**：查看引用覆盖、缺失事实点、原文依据和人工裁定；
6. **分析报告**：报告摘要、详细结论、追问清单、导出；
7. **评测面板**：内部开发与评测用途，不作为普通业务用户的主要入口。

首版不必把每个模块做成独立复杂页面。可以在现有工作台基础上使用左侧导航、中央内容区和右侧上下文面板逐步实现。

### 4.2 页面布局建议

#### 项目首页

- 项目名称、客户/场景信息、最近更新时间；
- 文件总量和清洗/索引状态；
- 最近一次分析报告；
- 待确认需求数量、证据缺失提醒；
- 「上传材料」「打开 AI 问答」「运行需求分析」等主要操作。

#### 资料库页面

- 文件名、材料类型、上传时间、处理状态、版本号；
- 状态至少包括：待处理、清洗中、待用户确认、索引中、可问答、失败；
- 点击文件查看原文、清洗后的文本和段落映射；
- 支持删除、替换、重新清洗和重建索引；
- 当材料被替换时，应明确提示旧版本是否仍被旧报告引用，不能静默覆盖证据来源。

#### AI 问答页面

- 对话区：用户问题、AI 回答、引用来源、未确认说明；
- 上下文选择：当前文件、选中多个文件、整个项目；
- 引用卡片：文件名、段落 ID、原文摘要、打开原文操作；
- 回答操作：复制答案、查看证据、转成需求候选、生成追问；
- 历史对话：按项目保存，并记录本轮使用的文件范围和清洗版本。

#### 需求分析页面

- 需求分类：显性需求、潜在需求、待确认；
- 需求字段：业务意图、描述、原文证据、影响对象、需求状态；
- F5 缺口与追问；
- F6 优先级维度和加权结果；
- F7 能力匹配结果及依据；
- 用户确认、编辑、否定、合并或拆分需求的入口；
- 所有重要修正保留 AI 原判断、人工判断和修改原因。

#### 证据审查页面

- 按需求展示其引用的全部段落；
- 对于合并多个事实点的需求，展示覆盖了哪些事实点、哪些尚未找到引用；
- 允许打开原文并人工确认；
- 不允许只凭相似度分数自动宣称引用可靠；程序检测应作为提示，复杂语义支撑关系仍需人工复核。

#### 分析报告页面

- 执行摘要；
- 关键需求集合；
- 显性/潜在需求；
- 优先级与评分依据；
- 产品能力匹配；
- 决定性、关键、普通三类待确认信息；
- 建议追问；
- 风险与证据争议；
- 引用索引和报告版本信息；
- 导出 Word/PDF（规划功能，需单独验收）。

### 4.4 可视化交互原型（补充）

之前在讨论中展示的「左侧工作导航 + 中央 AI 对话 + 右侧原文证据与下一步操作」结构，应该作为产品方案的一部分保留下来，而不只是聊天中的示意。对应的可点击 HTML 原型已单独提供：

- **[打开 AI 客户材料分析工作台交互原型](AI客户材料分析工作台_交互原型.html)**：下载 HTML 后用浏览器打开即可体验页面切换、模拟问答、查看原文、转成需求候选等交互。
- 原型页面包括项目总览、资料库、AI 知识问答、需求分析、证据审查、分析报告、质量概览和项目设置。
- **原型范围声明**：页面使用模拟数据，不连接 DeepSeek、不执行真实文件解析、RAG 检索或真实报告导出；它用于确认页面结构、信息层级与交互方向，不代表这些功能已经在现有代码中实现。

核心页面的初始布局如下：

```text
┌──────────────────┬─────────────────────────────────────────┐
│ 工作空间          │ 项目路径 / 搜索 / 上传材料                │
│                  ├─────────────────────────────────────────┤
│ 项目总览          │ AI 知识问答                    当前项目资料 │
│ 资料库            │                                         │
│ AI 知识问答  ←    │ 用户问题                                │
│ 需求分析          │ AI 回答 + 关键事实点                     │
│ 证据审查          │ ┌─────────────────────────────────────┐ │
│ 分析报告          │ │ 原文引用 · 文件名 · 段落编号 · 查看原文 │ │
│ 质量概览          │ └─────────────────────────────────────┘ │
│ 项目设置          │ 输入问题 / 发送 / 转成需求 / 生成追问      │
└──────────────────┴─────────────────────────────────────────┘

右侧上下文区域：本轮引用、资料来源、证据状态、待确认提醒与后续操作。
```

此原型是讨论版方案的可体验延伸，不替代本文件后续章节中的需求、技术设计、数据结构和验收标准。正式开发时仍需将每个按钮映射到真实接口与状态流转，并明确加载、失败、空结果和权限错误等状态。

### 4.3 主导航与主工作区的交互原则

- 从对话引用可以跳转到原文段落；
- 从原文段落可以反向查看它支持哪些需求或回答；
- 从需求详情可以打开引用它的对话和报告；
- 用户在聊天中发现新的信息，不直接悄悄改写正式报告，必须通过「加入需求候选」或「更新待确认事项」等明确操作；
- AI 问答结果默认是建议，不自动改变需求状态和最终报告。

## 5. 核心用户流程

### 5.1 流程一：建立项目与导入材料

1. 用户新建项目，填写项目名称和可选的行业/客户背景；
2. 上传或粘贴材料；
3. 系统识别文件类型，检查空文件、过长内容和读取失败；
4. 执行格式清洗，输出清洗预览；
5. 展示原文与清洗文本的对应关系；
6. 用户确认使用清洗结果，或手动修正后重新确认；
7. 系统建立可检索索引，生成索引版本；
8. 文件状态变为「可问答」。

关键原则：**不要让清洗后的文本脱离原文段落编号。** 所有段落、分块和引用都应带来源文件 ID、原文段落 ID 和文本版本。

### 5.2 流程二：针对知识库问答

1. 用户选定问答范围：当前文件、多个文件或整个项目；
2. 输入问题；
3. 系统从已清洗且已索引的材料中检索相关段落；
4. 对检索结果按相关性、来源和段落上下文进行整理；
5. 模型在检索证据范围内生成答案；
6. 系统执行引用格式和来源存在性校验；
7. 回答中列出关键结论、对应引用及不确定性；
8. 用户可以打开原文核实，或者将回答转成需求候选/追问。

若检索结果不足，系统应明确说明「现有材料不足以确认」，并提出需要补充的信息，而不是强行回答。

### 5.3 流程三：从问答进入需求分析

1. 用户从回答中选择「转成需求候选」；
2. 系统预填需求描述、类型和引用来源；
3. 用户核实其是否是真正的需求，而非背景、诉求或无关内容；
4. 需求进入草稿状态，不立即视为已确认；
5. 用户运行现有需求分析 Workflow，或将新信息加入下一次分析；
6. 系统对重复、相似、冲突的需求给出提示；
7. 用户审阅需求、缺口、优先级和能力匹配；
8. 经用户确认后，形成当前报告版本。

### 5.4 流程四：发现资料矛盾

1. 检索命中两份材料中相互冲突的表述；
2. 系统将两个来源并列展示，包含时间和来源；
3. 系统描述具体冲突点，不自行认定哪一方正确；
4. 自动创建待确认项，给出建议追问；
5. 用户确认后填写最终结论和依据；
6. 保留原始冲突与裁定历史。

### 5.5 流程五：生成并交付报告

1. 用户在需求分析页确认需求和状态；
2. 系统汇总关键需求、优先级、能力匹配和待确认项；
3. 执行引用覆盖检查，展示未覆盖事实点；
4. 用户处理重要警告或明确接受残余风险；
5. 系统生成报告版本；
6. 用户导出报告，并可继续回到对应需求或引用查看证据。

## 7. 知识库问答的产品规则

### 7.1 回答依据规则

1. 对项目材料事实的回答，应提供可以核验的原文引用；
2. 如果结论依赖多个事实点，尽量分别引用对应出处，不只引用一段看似相关的内容；
3. 如果没有找到足够依据，应明确写「材料中未找到足够证据」；
4. 不把模型常识或行业经验伪装成客户材料原话；
5. 如需给出分析推断，必须标注为推断，并说明依据与不确定性；
6. 材料存在冲突时，优先呈现冲突，再提示需要确认，不擅自决定哪份材料正确；
7. 原文和清洗文本不一致时，引用定位以原文为准，并提示可能存在清洗误差；
8. 用户修改的结论必须明确属于人工修正，不覆盖原始材料。

### 7.2 建议的回答结构

针对事实查询，推荐简短回答：

- **结论**：一句话回答用户问题；
- **依据**：引用一到数条原文，包含文件名与段落 ID；
- **判断边界**：材料未说明什么、有哪些不确定性；
- **下一步**：需要确认时给出一个具体追问。

针对跨材料分析，推荐结构：

- 已确认的一致信息；
- 存在差异或矛盾的信息；
- 每条信息的出处与时间；
- 当前无法判断的部分；
- 推荐向客户确认的问题。

### 7.3 引用卡片字段

每条引用至少保留：

| 字段 | 作用 |
|---|---|
| source_file_id | 稳定识别来源文件 |
| source_file_name | 前端显示文件名 |
| source_version | 引用基于哪个文件版本 |
| source_paragraph_id | 原文段落编号，例如 P7 |
| clean_paragraph_id | 清洗后段落编号，例如 D12，可选 |
| source_excerpt | 用于展示的原文摘录 |
| retrieval_score | 检索排序参考，不直接当作事实置信度 |
| citation_reason | 这段材料支持答案的哪一个要点 |

不能只存一条拼接后的文本而丢掉段落映射。否则后续的原文跳转、引用审查、文件更新和结果复现都会出现困难。

### 7.4 证据不足与冲突处理

| 情况 | 系统应做什么 | 不应该做什么 |
|---|---|---|
| 检索不到相关材料 | 明确材料未提及，建议补充信息 | 用常识补出客户事实 |
| 只找到部分证据 | 说明已知部分和未知部分 | 将部分覆盖说成完全确认 |
| 两份材料说法不一致 | 同时展示双方证据和时间 | 静默选择某一方 |
| 清洗疑似改变原意 | 提示用户检查原文 | 把清洗文本直接当唯一事实来源 |
| 文件已更新但索引未更新 | 阻止或提示使用旧索引 | 将新旧版本混合检索 |
| 用户问的是建议而非事实 | 将事实依据与建议分开写 | 把建议写成客户明确要求 |

## 8. 技术方案建议

> 本节是建议的逻辑结构，不代表这些组件已实现。实际实现时应先检查当前仓库目录、依赖和运行方式，再按最小改动原则落地。

### 8.1 总体架构

```text
Web 工作台
  ├── 项目管理与文件列表
  ├── 清洗预览与原文查看
  ├── AI 知识问答
  ├── 需求分析与报告
  └── 引用审查与评测面板
          │
          ▼
后端应用服务
  ├── 项目/文件服务
  ├── 文本清洗与段落映射
  ├── 索引构建服务
  ├── 检索服务
  ├── RAG 问答编排
  ├── 现有需求分析 Workflow
  ├── 引用校验与覆盖检查
  └── 报告生成与版本管理
          │
          ├── 结构化数据存储
          ├── 原始文件与清洗文本存储
          ├── 检索索引
          └── 模型/API 适配层
```

### 8.2 需要保留的模块边界

- **清洗模块**：输入原始内容，输出清洗文本、段落映射和清洗版本；不负责生成最终需求判断；
- **索引模块**：将经过确认的清洗文本转成可检索数据；不改写原始事实；
- **检索模块**：根据问题和范围返回候选证据段落，并保留来源元数据；
- **问答模块**：在检索证据基础上生成回答，不直接改变正式需求清单；
- **需求分析模块**：沿用现有固定 Workflow 与结构化输出；
- **证据模块**：检查来源存在、覆盖情况和用户审核状态；
- **评测模块**：离线对照固定测试集，不应和在线问答业务逻辑混为一体。

首期尽量通过新增独立模块完成，不要为了知识库功能重写现有分析 Workflow。

### 8.3 存储实体建议

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Project | project_id、name、created_at、status | 项目级隔离边界 |
| Document | document_id、project_id、filename、type、status、current_version | 文件元数据 |
| DocumentVersion | version_id、document_id、raw_text、clean_text、created_at、cleaner_version | 原文与清洗版本 |
| ParagraphMap | version_id、source_paragraph_id、clean_paragraph_id、source_span、clean_text | 保留清洗与原文映射 |
| RetrievalChunk | chunk_id、project_id、document_id、version_id、paragraph_ids、text、metadata | 检索分块 |
| Conversation | conversation_id、project_id、title、created_at | 对话会话 |
| Message | message_id、conversation_id、role、content、created_at | 对话消息 |
| AnswerCitation | message_id、chunk_id、source_paragraph_ids、claim_text | 回答引用关系 |
| AnalysisRun | run_id、project_id、workflow_version、prompt_version、created_at | 一次需求分析记录 |
| Requirement | requirement_id、run_id、category、description、status、source_refs | 需求条目 |
| HumanReview | entity_id、ai_value、human_value、reason、reviewer、created_at | 人工修正与留痕 |
| ReportVersion | report_id、project_id、analysis_run_id、version、created_at | 正式报告版本 |

这些是逻辑数据实体，首版不一定要全部建立独立数据库表；可以按照当前项目的存储方式做最小实现，但字段责任和关系应保持清晰。

### 8.4 检索策略建议

建议按两步推进：

**第一步：验证基础检索。** 做好段落切分、项目过滤、来源 ID、关键字匹配和结果排序。用真实的目标问题验证召回，不要只看页面能否返回答案。

**第二步：按测试结果升级。** 如果用户会大量使用同义表达、概念问题或跨文档问题，而关键字方式召回不足，再接入向量检索；如候选结果仍不够准确，再评估混合检索与重排序。选型以可测量的检索表现为依据，不为使用某种技术而添加复杂度。

检索服务的输入输出应标准化。例如：

```json
{
  "project_id": "project_001",
  "query": "客户是否明确要求数据不能离开内网？",
  "scope": {
    "document_ids": ["doc_001", "doc_002"]
  },
  "top_k": 5
}
```

返回结果必须包含文本和来源元数据，而不只是纯文本字符串。上面的字段是接口示例，不表示现有服务已采用该格式。

### 8.5 RAG 问答建议流程

1. 校验当前项目和文件范围；
2. 检查用户问题是否需要基于资料回答；
3. 检索最相关的段落，并保留对应来源；
4. 对重复片段去重，对多段上下文按来源和相关性组织；
5. 调用模型，根据提示词限定回答边界；
6. 要求模型对关键事实逐条关联引用；
7. 检查引用 ID 是否存在，答案是否包含可核验来源；
8. 对证据不足、明显冲突或引用不完整的回答添加提示；
9. 保存问题、检索范围、索引版本、答案和引用，方便后续复核。

初版可以先使用单次检索加生成，不需要立即建设 Agent、多轮自主规划或复杂工作流。先验证检索与引用可靠性，再决定是否需要复杂编排。

### 8.6 安全与配置

- API Key 只在后端环境变量或受控配置中读取，不写入前端页面和 Git；
- 日志默认避免保存不必要的完整客户原文；
- Demo 优先使用虚构或脱敏材料；
- 项目 ID 必须参与所有检索过滤，避免跨项目串资料；
- 删除文档时同步处理索引和引用状态，并保留必要的操作记录；
- 文件读取失败、索引失败、模型调用失败要有用户可理解的状态提示；
- 对外演示前检查密钥、测试数据、错误日志与导出文件，避免暴露敏感信息。

## 9. 评测与验收方案

### 9.1 两条链路分开评测

继续保留现有需求分析评测链路；新增知识库问答后，需要建立独立的问答测试集。不能用需求提取 F1 直接代表知识问答质量，也不能因问答体验改善就认定需求分析 Prompt 得到提升。

| 链路 | 主要评测对象 | 现有/新增指标 |
|---|---|---|
| 需求分析 Workflow | 需求提取、关键遗漏、优先级、能力匹配和证据 | 现有 ①②③⑤⑥⑦ 等指标，继续按原口径记录 |
| 知识库问答 RAG | 检索是否找对材料、回答是否有依据、引用是否准确 | 新增命中率、引用正确率、答案支撑率、拒答合理性、原文定位成功率 |
| 工作台交互 | 用户能否理解状态并完成任务 | 上传成功率、清洗确认成功率、问答完成率、错误恢复率、任务耗时 |

### 9.2 建议的首版问答测试集

先做一份规模可控的内部测试集，建议至少包含以下类别：

| 类别 | 示例问题 | 要检查的能力 |
|---|---|---|
| 明确事实查询 | 客户是否说过不能出内网？ | 直接找事实并引用原文 |
| 数字/日期查询 | 客户提到的上线时间是什么？ | 数值与时间不能编造或混淆 |
| 多段证据 | 自动预警的触发条件有哪些？ | 多个事实点引用覆盖 |
| 多文件对照 | 后续邮件是否改变了会议中的上线安排？ | 跨文件比对与时间顺序 |
| 矛盾材料 | 两份材料对预算的说法是否一致？ | 识别冲突、不擅自选边 |
| 无答案问题 | 客户是否指定了某个未提及的供应商？ | 证据不足时不编造 |
| 范围过滤 | 只在指定邮件中查找预算 | 遵守用户设定的材料范围 |
| 清洗异常 | 原文和清洗文本存在差异 | 发现并提示清洗风险 |
| 误导性问题 | 用户把推断包装成客户原话询问 | 区分事实、推断和用户假设 |
| 需求转化 | 把已确认的要求整理成需求候选 | 需求来源明确且状态正确 |

### 9.3 首版验收门槛（建议值，需随测试结果校准）

这些门槛是产品工程验收目标，不是已经验证的现有成绩：

- 文件上传、清洗状态和索引状态能够稳定显示；
- 每条事实型回答均有引用或明确标注无足够证据；
- 所有输出引用 ID 必须能在当前项目、当前版本中找到；
- 预设的无答案问题不得编造材料事实；
- 预设的矛盾问题必须展示冲突，不能静默选边；
- 对话范围设置必须生效，不能读取未选中文件或其他项目材料；
- 对人工确认与修改保留清晰记录；
- 新功能加入后，现有 28 项测试继续通过；
- 新增问答测试案例、结果和失败项独立留档。

对回答事实正确率、引用充分率等指标，先用人工标注小测试集建立基线，再决定正式阈值。不能仅凭模型自评或一次演示宣称问答功能可靠。

### 9.4 现有指标的处理纪律

- 保持 `m4-freeze` 基线记录，不用新增功能的结果覆盖历史指标；
- Prompt v1.7.1 先冻结，不与知识库问答功能同一轮修改；
- `metrics v1.5` 的引用完整率可以用于检查既有分析结果，但要单独注明它的定义；
- 新增引用检查若改变评测器逻辑，必须独立版本化、编写单测、离线复算并做回归；
- FINAL 已揭晓结果，只能作为固定回归集，不再充当新的盲测证据；
- 如后续需要证明新 Prompt 的泛化表现，应另建全新未见案例集。

## 10. 版本规划与实施路线

### 10.1 P0：数据与证据基础

**目标：** 保证清洗后的每个文本片段都能回到原文，为知识库问答、分析报告和引用审查提供共同基础。

任务：

1. 检查现有清洗输出是否稳定保留原文 P 编号和清洗后 D 编号；
2. 明确文件、文件版本、段落映射和项目 ID 的字段约定；
3. 为每条分析引用统一来源结构；
4. 明确删除、替换文件后的索引更新策略；
5. 定义检索模块接口，不先锁定复杂底层方案。

完成标准：任何需求或问答引用都能定位到具体文件版本和原文段落；现有分析功能无回归。

### 10.2 P1：知识库 + AI 对话 MVP

**目标：** 让用户能够对清洗后的项目资料提问，并通过引用核对答案。

任务：

1. 创建项目资料列表；
2. 复用现有清洗能力并增加清洗确认状态；
3. 对已确认材料建立项目级索引；
4. 实现范围选择、问答输入与返回；
5. 对答案添加来源卡片和原文跳转；
6. 增加证据不足提示；
7. 保存对话记录和本次检索范围；
8. 建立问答小测试集并记录错误。

完成标准：用户能选定项目资料、提出问题、查看有来源的答案，并在回答找不到依据时获得清晰提示。

### 10.3 P2：问答与需求分析闭环

**目标：** 让问答成果进入现有结构化分析，不造成第二套互不关联的数据。

任务：

1. 增加「转成需求候选」操作；
2. 将回答与需求条目建立来源关系；
3. 允许用户生成待确认项和下一轮追问；
4. 对新旧需求提供重复/冲突提示；
5. 将用户确认后的需求加入分析草稿或下一次 Workflow 输入；
6. 保留 AI 原判断与人工修正历史。

完成标准：从问答生成的需求候选可以进入正式分析页查看和修订，且始终保留原文证据。

### 10.4 P3：引用审查 + 报告导出

**目标：** 提高引用完整性与演示交付感。

任务：

1. 利用现有完整率口径，对多事实点需求提示引用缺失；
2. 展示「已覆盖事实点 / 缺失事实点」；
3. 自动修复动作必须先生成候选，避免没有证据时强制补引；
4. 为重要问题提供人工确认入口；
5. 增加 Word/PDF 导出；
6. 报告中保留引用、版本、未确认事项和生成时间。

完成标准：报告可导出并可追溯；引用覆盖警告能指出具体缺失来源，不只是展示一个总分。

### 10.5 P4：进阶能力

可纳入后续版本，当前不承诺实现：

- 多文件批量上传与批处理分析；
- 多项目横向比较；
- 多人协作、完整 RBAC 与审批；
- 自动订阅新材料、增量索引；
- 多轮需求演化与历史对比；
- 复杂任务分解、多 Agent 或自主规划；
- 更复杂的跨项目分析与数据统计。

这些能力应在核心链路经测试后再评估，不因为看起来先进就提前加入。

## 11. 明确不做的事项与范围边界

首版明确不做：

1. 不把产品做成通用聊天机器人；
2. 不开放跨项目全局检索；
3. 不允许 AI 问答自动修改正式需求结论；
4. 不让模型根据常识补全客户未提供的事实；
5. 不默认开启自主规划、多 Agent 或长时间循环；
6. 不同时修改当前优先级 Prompt、能力匹配 Prompt 和知识问答链路；
7. 不在没有测试的情况下承诺引用完整率一定达到某个数值；
8. 不把已揭晓的 FINAL 数据集继续当作新盲测集；
9. 不在 Demo 中接入未经脱敏的真实客户材料；
10. 不在首期建设复杂的组织、租户和权限管理系统，但项目数据隔离必须生效。

新增需求先记录在候选清单中，只有在当前阶段验收后才决定是否纳入下一阶段。

## 12. 风险与应对

| 风险 | 表现 | 应对方式 |
|---|---|---|
| 清洗过程丢失上下文 | 引用只能定位到清洗文本，无法回原文 | P0 先建设段落映射；清洗结果用户确认后再索引 |
| 检索召回不足 | 问答找不到语义相近的内容 | 用问答测试集评估；必要时增加向量检索/混合检索 |
| 答案有引用但不受引用支持 | 引用存在，却无法证明结论 | 区分引用存在性、覆盖完整性和语义支撑性；复杂项人工复核 |
| 跨文件证据冲突 | 模型挑选一条来源并忽略另一条 | 冲突并列展示，自动生成待确认项 |
| 误把推断当事实 | 将业务常识写成客户原话 | 输出层标注事实/推断/待确认，缺依据则降级 |
| 引用完整率低 | 只引用最明显的出处 | 以完整率检查缺失事实点，并给出可操作的补证建议 |
| 评分规则副作用 | 改 Prompt 后某指标改善但其他案例回退 | 当前评分线先冻结，单变量、双轮或逐轮回归并记录新偏 |
| 复杂度过高 | 先做 Agent、权限或多数据库，核心闭环没完成 | 先完成 P0/P1；每阶段按验收标准决定是否扩展 |
| API 成本与响应时间 | 多轮调用增加费用或等待 | 记录调用、token、成本与耗时；先做单轮问答和必要校验 |
| 数据安全 | API Key 或客户材料泄露 | Key 仅后端读取，Demo 使用虚构/脱敏材料，日志最小化 |
| 文档与代码版本不一致 | 文档称已完成但代码未实现 | 每项功能记录状态、代码提交、测试和已知限制 |

## 13. 产品成功指标

建议分为三层，不用单个 F1 覆盖所有产品价值。

### 13.1 业务任务指标

- 用户从进入项目到找到指定事实的任务完成时间；
- 单次材料分析中需要人工补查的次数；
- 有多少问答结果被用户转成需求候选或追问；
- 用户在查看报告时能否直接定位来源；
- 用户是否需要重复复制粘贴材料到不同工具。

这些指标应通过可控任务测试或使用记录采集，首期不假设已有真实业务数据。

### 13.2 问答质量指标

- 检索命中率/召回表现；
- 回答事实正确率；
- 引用存在性和原文定位成功率；
- 引用完整率；
- 答案受引用支撑的比例；
- 无证据问题的合理拒答率；
- 矛盾材料识别率；
- 平均响应时间与单次调用成本。

### 13.3 需求分析指标

继续沿用现有指标 ①②③⑤⑥⑦，保持各项口径可追溯，不能因为新页面或问答功能上线就自动修改这些指标定义。

## 14. 推荐开发任务拆分

建议后续按小任务独立提交，不一次把整个产品交给代码助手自由重构。

### Task 1：梳理现有数据和来源映射

交付：当前数据流图、清洗输出结构、引用字段说明、现有测试清单。  
验收：确认哪些字段已经有、哪些需新增；不改业务行为。

### Task 2：建立项目/文件/版本的数据契约

交付：项目 ID、文件版本、原文段落 ID、清洗段落 ID、索引状态的数据结构。  
验收：已有输入可转换为新结构；旧分析流程继续通过。

### Task 3：完成资料库页面

交付：文件列表、清洗预览、状态展示、查看原文和清洗版本。  
验收：处理状态明确；任何清洗文本可回到原文；错误提示可理解。

### Task 4：完成基础检索服务

交付：按项目和选定文件检索清洗文本，结果附来源元数据。  
验收：写基础检索单测，证明查询范围过滤有效；检索结果可复现。

### Task 5：完成引用式 AI 问答

交付：问答界面、模型调用、来源卡片、原文跳转、证据不足提示。  
验收：事实型回答可核验；无答案题不编造；项目隔离有效。

### Task 6：建立问答质量测试集

交付：至少覆盖事实、数字、多证据、跨文件、矛盾、无答案等问题的测试样例和人工标准答案。  
验收：每次问答链路改动都可重复评测；失败样例单独归档。

### Task 7：连接需求分析流程

交付：回答转需求候选、生成追问、链接报告条目。  
验收：未经用户确认不改变正式报告；每条候选有来源。

### Task 8：引用完整性和报告导出

交付：缺失事实点提示、人工审查、Word/PDF 导出。  
验收：导出内容与页面版本一致，引用仍能被识别和核查。

每个任务完成后应记录：变更范围、涉及文件、测试结果、人工验收结果、已知限制、成本/耗时（如调用模型）和 Git 提交。

## 16. 最终建议

产品下一阶段不应该继续把主要精力全部投入到⑤优先级跳档的 Prompt 修复。已有实验表明该问题连续两轮改规则未通过，当前应保留 v1.7.1 作为现役基线并如实挂账。

更值得投入的方向是将现有的需求分析能力升级为可实际操作的工作台：

1. 先打通原文、清洗文本和段落引用的统一数据基础；
2. 在已确认材料上建立项目级知识库问答，回答能引用原文；
3. 让对话结果可以转成需求候选、待确认事项和追问；
4. 用引用覆盖检查帮助用户发现证据不全的问题；
5. 最后再补报告导出、批处理等交付增强能力。

**最终产品体验应该是：用户不再需要在原始文件、清洗文本、聊天窗口和需求报告之间反复复制信息，而是在一个项目工作台内完成检索、核实、分析、确认和交付。** 这一主线既保留当前项目的评测与证据能力，也能让新增 Web 知识库和 AI 对话有明确业务价值。
