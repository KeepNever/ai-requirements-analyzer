# 03 · 版本管理与演进说明

> 用途：回答「这个项目怎么做的版本管理」「第一版和第二版分别是什么、怎么演进」——
> 也是面试时讲工程规范的一页材料。

---

## 一、两代产品定义

| | V1：评测驱动的需求分析引擎 | V2：可使用的分析工作台 |
|---|---|---|
| 时间 | 2026-10 上旬（M0~M4） | 2026-10-19 起（P1 进行中） |
| 核心问题 | 「这个 LLM 应用可靠吗？」——先把质量测准 | 「这东西能用起来吗？」——把引擎做成软件 |
| 产出 | 三节点分析 Pipeline + 17 案例三层验证集 + 六指标评测体系 + 68 项测试 | 版本化存储层 + 资料库页 + 检索 + 引用式多轮问答 + 工作台界面 |
| 分界提交 | `ecf149f`（正式验证集盲测，V1 收官） | `c69c6a3`（V2 立项，收编方案与原型） |

**关系**：V2 不是重写。V1 的清洗器、分析 Pipeline、评测器原样是 V2 的引擎；V2 在外面加了存储层（版本化）、资料库、问答与界面。所有 V1 评测资产（17 案例、GT、指标快照）在 V2 里继续有效。

## 二、版本坐标体系

项目里同时存在多条独立版本线，各自演进互不捆绑：

| 组件 | 当前版本 | 说明 |

| 测试 | 68 项 | 每轮迭代必须全绿才允许合入 |

## 三、Git 实践

- **单 main 分支**：个人项目规模下分支开销大于收益；质量靠「68 测试全绿才允许 commit」把守，回退靠 tag。
- **提交信息规范**：单行包含「类型 + 做了什么 + 验收状态」——例如 `M4-R1 优先级跳档锚点实验：…，判定未通过，v1.8去留待拍板`。失败实验同样留档（诚实记录是纪律的一部分）。
- **里程碑打 tag**：V1 用 `mN-freeze`（阶段冻结），V2 用 `v2-taskN-*`（任务级）+ `v2.0.0`（现役版本）。
- **回退操作**：`git checkout <tag> -- src/` 可恢复任意历史版本源码；数据层永不覆盖（版本化存储自带回溯）。

## 六、下一阶段的版本规则（预先声明）

- Task 5（问答测试集）、报告导出、场景模板完成后，分别打 `v2-task5-*`、`v2-feature-export`、`v2-feature-scene`；
- 功能级验收（曦确认）后才打 tag，中途提交不 tag；
- 破坏性变更（契约修改）必须先改 `01_Task1` 契约文档并过审，再动代码——Task 1~4 的流程延续。
