## 1. 项目概述与决策结论

### 1.1 项目从哪里来

项目最初是「AI 客户需求分析助手」，用于把客户会议转写、微信记录、访谈笔记、邮件等非结构化材料转为结构化需求分析结果。随着 V2 建设，项目已经不止于一次性分析，而是逐步扩展成包含资料管理、清洗预览、引用式 AI 问答、需求分析、历史版本和评测看板的 Web 工作台。

### 1.2 当前的产品定位

**AI 客户材料分析工作台：面向 B 端售前、产品经理和解决方案人员，帮助用户把分散的客户材料转化为可检索、可核验、可分析、可交付的业务信息。**

产品不应只做一个「把文件上传到知识库再聊天」的页面。知识问答是入口之一，核心价值应贯穿：

- 找得到：从多份客户材料中检索相关事实。
- 答得有据：答案可以回到具体文档、版本和原文段落。
- 分得清：区分材料事实、合理推断、尚待确认的信息。
- 分析得出：把材料整理成需求、风险、能力匹配和下一步追问。
- 交付得了：将分析结果汇总为结构化报告，保留历史运行和证据链。

### 1.3 当前决策

**下一步优先做 Task 5：建立 AI 问答评测集与当前版本基线。** 在基线出来之前，不急于更换检索技术，也不同时调整问答 Prompt、检索、上下文组装和引用规则。

建议主线顺序：

1. Task 5：问答评测集与基线。
2. Task 6：根据错误分布，选择一个检索或生成问题进行单变量优化。
3. Task 7：完善引用定位、证据审查和用户反馈交互。
4. Task 8：增加第二个场景模板「客户服务对话诊断」，验证底层能力复用。
5. Task 9：完善 Word 报告导出和演示体验。
6. 求职作品集物料：贯穿整理，不必等所有功能完成后才开始。

上述为建议路线，不意味着后续任务已经实现。每个任务需达到各自验收标准后才能进入下一阶段。

### 2.3 现阶段不主动重启的问题

| 问题 | 当前处理方式 | 原因 |
|---|---|---|
| ⑤ 优先级向上跳档 | 暂时挂账，现役 Prompt 恢复/保持 v1.7.1 | R1 与 R2-a 两轮 Prompt 实验未达到目标，并引入新偏差；暂不继续堆规则 |
| F7 矛盾材料强行归类 | 留作后续独立候选 | 与优先级优化分开，不能在问答质量迭代中顺手改变既有分析基线 |
| ⑦ 引用不完整 | 已记录为需求分析侧问题；先不要与问答评测混为一个指标 | 问答的引用支撑与需求分析的多事实点完整率相关，但对象和评测口径不同 |

### 2.4 已知的问答侧技术现状

- 检索采用段落级 n-gram 关键词匹配，目前优先适用于材料规模较小的场景。
- 检索无命中时有三层回落：历史轮次相关引用段落、小材料全量段落、大材料证据不足。
- 回答可以引用检索候选中的 D 编号，EVD-01 会校验编号有效性。
- 多轮上下文会带入最近 5 轮，但仍需测试长对话、指代消解和历史内容污染。
- 目前缺少系统化问答质量评测集与可比较的问答指标基线。

## 3. 产品定位、目标用户与核心价值

### 3.1 目标用户

**主要用户：**

1. B 端售前/解决方案人员：整理客户访谈、识别需求和方案前提，准备下一轮沟通问题。
2. B 端产品经理：阅读客户反馈、分析需求优先级、整理产品能力差距。
3. 项目交付/客户成功人员：回顾客户沟通记录、查找承诺、定位争议及待跟进事项。

**第一阶段不重点服务：** 大规模企业知识中台、跨组织权限复杂的多人协作、数百万文档搜索、企业级 SSO 和完整知识治理。那些能力需要另外的安全、部署和运维设计，不应假设当前个人作品集原型已经具备。

### 3.2 核心用户任务

用户的真实工作并非只问「材料里写了什么」，而是需要完成：

- 把多份来源不同的材料放到同一项目下。
- 快速找到客户说过的关键事实和约束。
- 对引用原文进行核对，避免 AI 把推断写成事实。
- 看清不同材料之间的冲突，以及还缺什么信息。
- 形成需求、优先级、能力匹配和追问清单。
- 将结论和依据整理成可以交给同事、客户或面试官查看的报告。

### 3.3 产品差异化主张

普通知识库更偏向「上传文件、检索并回答问题」。本项目应突出以下差异：

- **证据先行：** 每个可核验回答都能定位到来源文档、版本和段落。
- **事实分层：** 明确区分原文事实、推断、待确认信息。
- **分析闭环：** 从问答结果可以进入需求分析、待确认清单和报告。
- **过程可复现：** 文档版本、分析运行、模型版本和使用成本有记录。
- **质量可衡量：** 不只看演示是否顺畅，还建立问题—证据—答案的测试集。

### 3.4 产品一句话介绍

**一个面向 B 端客户材料的 AI 工作台，帮助用户从会议记录、聊天记录和邮件中查找事实、核验证据、提炼需求、识别风险，并生成可追溯的分析结果。**

## 4. 产品目标与本阶段不做什么

### 4.1 本阶段目标

1. 建立一套可以重复运行、定位错误并比较版本的问答评测基线。
2. 根据评测结果解决一个明确且影响较大的问答问题，而不是泛泛优化「AI 感觉更聪明」。
3. 让用户更容易从回答跳转到来源证据，并对有问题的回答进行反馈。
4. 保持现有需求分析主链路和评测体系稳定。
5. 为后续场景模板和 Word 报告交付打下基础。

### 4.2 非目标

本阶段不做：

- 不重写已有需求分析 Prompt，不重启 ⑤ 优先级优化线。
- 不把 F7 矛盾场景规则和引用式问答规则混为一个实验。
- 不因技术潮流立即引入向量数据库、复杂 Agent 或多 Agent。
- 不做完整企业级多租户权限、SSO、计费与运维系统。
- 不自动把用户反馈直接写入 GT 或自动改 Prompt。
- 不宣称小样本评测结果证明产品在所有行业普遍有效。

## 5. 目标用户流程与核心场景

### 5.1 主流程 A：客户材料问答

1. 用户进入工作台，创建或选择一个项目。
2. 上传或粘贴会议纪要、聊天记录、邮件等材料。
3. 系统清洗文本，展示原文与脱敏清洗文本对照，并提示解析异常。
4. 文档保存为一个版本，建立 P-D 映射和检索索引。
5. 用户在 AI 问答页选择项目/文档范围并提问。
6. 系统检索段落、组装证据、生成回答并进行 EVD-01 引用校验。
7. 回答展示引用卡片；用户可以打开原文定位、检查来源和提出追问。
8. 用户可以把答案转为需求、待确认事项或行动项（阶段二能力）。
9. 用户可查看历史会话，并导出或复制整理结果。

### 5.2 主流程 B：客户需求分析

1. 用户选择材料或粘贴新材料。
2. 预览清洗与脱敏结果。
3. 触发既有分析 Workflow。
4. 查看清洗、提取、分析和报告节点的中间产物。
5. 查看需求清单、优先级、能力匹配、待确认信息。
6. 点击证据定位到源文档和具体段落。
7. 形成分析报告并保留运行历史。

此流程是现有产品的核心资产。本阶段新增问答能力不能破坏既有输出结构与行为。

### 5.3 主流程 C：多材料交叉核对

用户选定一个项目的多份材料后，提问例如：

- 「客户对上线时间的说法前后是否一致？」
- 「哪些系统的数据接口还没有确认？」
- 「谁提出了预算限制？原文依据是什么？」
- 「请列出目前已经确认与仍未确认的事项。」

系统应该：

- 对每份被引用材料明确标识名称和版本。
- 区分材料直接陈述与系统归纳。
- 对冲突内容并列展示，不自行替客户裁定哪一方正确。
- 对证据不足的部分明确说无法从现有材料确定。

### 5.4 主流程 D：服务对话诊断（后续模板）

上传服务对话后，系统按场景模板输出：

- 客户核心诉求。
- 具体问题和触发事件。
- 情绪/风险信号（只依据文本，不做过度心理推断）。
- 已承诺的动作及责任人（材料未提及则留空或待确认）。
- 尚缺信息及建议追问。
- 原文证据与引用。

该模板属于后续扩展，先复用现有清洗、引用和问答底层，不重新建设另一套引擎。

## 6. 产品信息架构与页面规划

### 6.1 总体导航

建议一级导航保持精简：

1. **工作台**：新材料输入、清洗预览、触发分析。
2. **项目资料库**：项目、文档、版本、分析运行树。
3. **AI 问答**：选择材料范围、对话、引用和历史会话。
4. **需求分析**：查看当前或历史分析报告。
5. **评测面板**：需求分析评测与问答评测分开呈现。

### 6.2 工作台首页

**目标：** 让用户清楚知道下一步做什么，不必理解底层节点和术语。

应包含：

- 「新建项目 / 选择项目」入口。
- 输入框或文件上传入口。
- 清洗预览与 PII 脱敏提醒。
- 最近项目和最近分析。
- 快捷动作：开始问答、开始需求分析。
- 明确提示当前操作会使用哪些文件和版本。

**验收标准：** 新用户能在不先阅读使用说明的情况下完成一次材料输入并进入清洗预览；不能在上传后悄悄覆盖既有文档版本。

### 6.3 资料库 `/library`

建议页面分为三部分：

- 左侧：项目/文档/版本/分析运行树。
- 中间：当前选中文档的原文、清洗文本和段落编号。
- 右侧或抽屉：版本元数据、清洗统计、PII 处理状态、来源映射。

重要交互：

- 能区分原始文本与脱敏文本。
- 能看出某个 D 编号合并了哪些 P 段落。
- 能切换不同 DocumentVersion。
- 能查看某一分析运行使用的文档版本。
- 缺少源文档或映射时要显示异常状态，不能伪装为完整引用。

### 6.4 AI 问答 `/chat`

页面建议包括：

- 当前项目和材料范围选择器。
- 对话区。
- 回答中的引用卡片。
- 点击引用后出现的证据抽屉：文档名、版本、P/D 编号、脱敏文本、相关上下文。
- 对话历史入口。
- 「有帮助 / 答案错误 / 引用不支持 / 信息遗漏」反馈入口。
- 明确的「材料没有提及」或「材料存在矛盾」提示样式。

不应把所有原文段落完整铺在回答区，否则信息密度过高。引用默认折叠为简洁卡片，用户点击后再展开上下文。

### 6.5 需求分析页

继续沿用现有的分析流程视图和报告结构。增量优化优先做：

- 需求条目和原文证据可互相跳转。
- 明确区分高优先级建议与产品/项目的最终决策。
- 待确认事项可以导出为单独清单。
- 可以显示本次分析所使用的文档版本和 Prompt 版本。

本阶段不修改优先级评分算法及现有 GT 口径。

### 6.6 评测 Dashboard

把两套评测明显分开：

**需求分析评测：** 保留现有指标 ①②③⑤⑥⑦，以及 MAIN / DEV / HOLD / FINAL 的身份与说明。

**AI 问答评测：** 新增独立区块，显示测试集版本、测试题数量、答案支持率、证据召回、引用有效率、引用支撑率、拒答准确率、多轮追问通过率和错误分类。

不能把问答评测指标与需求分析指标合并为单一「总分」，也不要用需求分析的 F1 作为问答质量的替代指标。

## 7. 核心功能需求

### 7.1 文档管理

- 一个 Project 可拥有多个 Document。
- 一个 Document 可有多个 DocumentVersion。
- 原文、清洗文本和映射随版本保存，不因重跑被覆盖。
- 上传相同内容时提示已有副本，不创建空版本。
- 同名但内容不同的文件，要求用户选择新建文档还是追加版本。
- 每次分析 Run 要记录使用的文档版本组合。

### 7.2 清洗与脱敏

- 支持带 P 编号材料，也支持无编号的粘贴文本。
- 无编号时按既定规则自动编号，过滤纯时间戳行并保留说话人前缀。
- `raw_text` 仅用于后端审计与证据核验，不直接进入 LLM 输入或前端展示。
- `clean_text` 用于默认检索、LLM 输入与前端展示。
- 清洗异常、段落为空、材料过长或可疑截断时给出明确提示。
- 刷屏合并等操作必须保存完整的 P-D 关系和被合并来源，不得静默丢失原文证据。

### 7.3 知识库检索

当前先保留关键词检索。检索模块需要：

- 记录本次查询的项目/文档范围。
- 返回真实存在的段落 ID、文档 ID 和版本 ID。
- 记录检索命中与回落路径，方便评测和诊断。
- 对小材料的全量回落设置明确上限，防止材料增长后将过多内容送入模型。
- 多轮追问可以参考上下文，但引用证据必须来自当前允许的材料范围。
- 检索索引应能按 DocumentVersion 重新构建，不能把新旧版本段落混用。

### 7.4 引用式问答

- 生成答案前先组织检索证据。
- 模型只能使用系统提供的可引用段落编号。
- 输出后进行引用 ID 校验。
- 仅编号有效不代表内容一定支持答案，后续评测必须检查语义支撑。
- 无证据、证据不足、证据冲突是不同情形，应分别表达。
- 如果答案含多个事实陈述，应尽量为每个关键事实提供相关证据。
- 前端不显示 raw_text；引用原文应使用脱敏后的文本。
- 引用必须保存 document_id、version_id、P/D 编号，不能只显示 D001 这样的局部编号。

### 7.5 多轮对话

- 支持指代类追问，例如「那它的限制呢」「刚才提到的时间是什么」。
- 支持总结类追问，例如「总结一下」「列成表格」。
- 历史上下文进入 LLM 时，应有轮数和 Token 上限。
- 历史消息不意味着旧证据自动有效；回答引用仍需绑定明确文档版本。
- 新一轮用户切换项目或材料范围时，应避免继续引用上一个范围内的证据。
- 会话可以恢复查看，必要时能区分消息、答案和引用列表。

### 7.6 需求分析闭环

- 保持当前分析 Workflow 原有行为。
- 从问答答案转入需求分析的能力可后续增加，不应直接自动改写 GT。
- 「转成需求」「加入待确认」「生成追问」等操作需要用户主动确认。
- 所有人工修正应记录修改前后内容、时间和来源；HumanReview 界面可以后续建设。

### 7.7 报告交付

- 当前先保留 `report.md`。
- Word 导出作为后续任务，使用与页面报告一致的结构和引用。
- 报告应包含分析所用材料及版本、生成时间、关键结论、待确认项和引用。
- 对未知信息、冲突材料和未经验证的推断要保留说明。

## 8. AI 问答评测方案（下一步优先任务）

### 8.1 为什么先评测

目前已有 68 项代码测试全绿，但代码测试主要验证程序结构、校验逻辑和异常处理。AI 答案是否正确、是否完整、引用是否支撑答案，需要专门的问答测试集。

先建立基线能回答三件事：

1. 当前版本到底在哪些问题上表现好或差。
2. 错误主要来自检索、上下文组装、答案生成还是引用处理。
3. 下一轮只该改哪个环节，避免多个模块同时变化后无法归因。

### 8.2 测试集规模与数据划分

建议第一版建立 **30 道问答用例**。由于样本仍小，结果只作为内部开发基线，不作为普遍效果声明。

建议划分：

- **DEV：20 题**，用于分析错误和反复调优。
- **LOCKED：10 题**，由人工审定问题和标准证据后锁定；优化期间不查看逐题具体结果，不据此修改系统。

如果 10 题在业务类型或难度上的覆盖不足，可以先补充问题，但不能在看过锁定集结果后临时调题来获得更好分数。锁定集揭晓后，后续若继续优化，则把它转为固定回归集，并另建新锁定集。

### 8.3 用例覆盖建议

| 类型 | 建议题数 | 检查重点 | 示例问题 |
|---|---:|---|---|
| 单事实查找 | 5 | 时间、金额、人员、系统名称是否提取准确 | 客户说的上线时间是什么？ |
| 语义改写/词汇鸿沟 | 4 | 提问与原文措辞不同能否找对证据 | 客户是否希望减少人工核对？ |
| 多段证据汇总 | 4 | 是否找到支撑答案所需的全部事实段落 | 客户提出了哪些部署约束？ |
| 多文档交叉核对 | 4 | 文件与版本是否混淆，能否处理冲突 | 两份材料对上线时间的说法是否一致？ |
| 多轮追问 | 4 | 指代承接、总结、继续追问是否有效 | 那个方案还有什么限制？ |
| 证据不足/未提及 | 3 | 是否诚实说无法确定，而非补造内容 | 客户的具体预算是多少？（材料未提及） |
| 矛盾证据 | 3 | 是否如实呈现不一致，而不是自行选边 | 客户最终确认的时间是哪一天？（材料中有冲突） |
| 汇总与行动项 | 3 | 总结是否遗漏关键内容，行动项是否有证据 | 请总结已确认事项和待跟进问题。 |
| **总计** | **30** | | |

若第一版只覆盖单文档，可以将多文档题暂时作为规划项，但在宣称具备稳定多文档问答能力前，必须补足对应测试。

### 8.4 每道题必须保存什么

每条问答用例至少包含：

- `question_id`：唯一编号。
- `dataset_split`：DEV 或 LOCKED。
- `project_id`、`document_version_refs`：问题允许使用的项目和文档版本。
- `question`：用户原始问题。
- `expected_answer_points`：标准答案的关键要点，不要求字面完全相同。
- `expected_citations`：必须或可接受的来源文档、版本和段落 ID。
- `evidence_sufficiency`：`answerable`、`insufficient` 或 `conflicting`。
- `expected_behavior`：回答、部分回答、明确未知或并列呈现冲突。
- `notes`：容易误判的地方。

GT 应先依据原始材料独立起草，再复核预期答案与证据。不要根据当前 AI 已经给出的答案反过来写标准答案。

### 8.5 评测指标定义

| 指标 | 定义 | 主要定位的问题 |
|---|---|---|
| 检索证据召回率 | 预先标注的关键证据段落中，有多少进入实际检索结果 | 召回遗漏、词汇鸿沟、检索范围错误 |
| 引用有效率 | 引用中确实存在于指定文档版本的比例 | 编造编号、版本串用、文档错配 |
| 引用支撑率 | 人工判断能真正支撑对应陈述的引用占比 | 引用虽存在但与结论无关 |
| 答案完整性 | 标准答案要求的关键要点中，实际覆盖的比例 | 遗漏、过度概括、部分回答 |
| 无依据陈述率 | 答案中缺少材料支持的事实陈述占比 | 模型补全、推断当事实 |
| 拒答/不确定判断准确率 | 对材料未提及、证据不足或相互矛盾的问题，处理是否符合预期 | 不该答时强答、证据冲突时擅自选边 |
| 多轮追问通过率 | 预先标注的多轮测试中，是否正确承接上下文并引用有效证据 | 指代丢失、上下文污染、历史证据误用 |
| 端到端通过率 | 每道题是否同时满足答案、证据与行为标准 | 用户最终是否获得可信结果 |

### 8.6 建议的初始验收门槛

下面是建议的项目内初始目标，需在第一轮基线跑分后评估可行性。它们不是当前已达到的成绩，也不是行业通用标准。

- 引用编号与文档版本有效性：**100%**；无效引用必须被拦截或明确标记。
- PII 泄露：**0 次**。任何一次 raw_text 泄露到前端或 LLM 输入都应阻断发布。
- 检索证据召回率：首轮目标 ≥ 0.80。
- 引用支撑率：首轮目标 ≥ 0.80。
- 答案完整性：首轮目标 ≥ 0.80。
- 拒答/不确定判断准确率：首轮目标 ≥ 0.80。
- 多轮追问通过率：首轮目标 ≥ 0.80。

不要只汇总平均值。必须同时展示每道题的结果和错误分类，因为 30 题的分母依然有限，单个问题就可能明显影响比例。

### 8.7 评测运行纪律

1. 固定当前问答 Prompt、检索参数、模型和材料版本，保存基线。
2. 记录实际检索到的段落、最终组装进 LLM 的证据、原始回答、校验后回答与引用。
3. DEV 用于迭代，LOCKED 结果在方案锁定前不查看。
4. 一轮只修改一个主变量；例如只改检索归一化，不同时改 Prompt 和引用校验。
5. 对有随机性的关键版本可重复运行两次，若逐题结果明显不一致，标记为不稳定，不挑选更好的一次报告。
6. 每轮新增指标必须沿用固定口径；如指标定义改变，旧新口径并列报告，不覆盖旧数据。

## Task 6｜根据基线进行一次单变量优化

**优先级：P1，必须由 Task 5 数据驱动。**

### 触发条件

只有当错误分布显示某类问题占比明显，才选择优化方向。不预先承诺必须使用向量检索。

### 可能的优化分支

| 评测发现 | 优先尝试的方向 | 本轮不同时做的事 |
|---|---|---|
| 预期证据未被检索到，且是词语不同导致 | 关键词归一化、同义词或轻量查询扩展 | 不同时改生成 Prompt |
| 证据已检索，但排名不合适 | 调整关键词分数或排序规则 | 不同时引入整套新检索架构 |
| 证据召回足够，但回答遗漏 | 优化证据打包与答案结构 | 不直接调低拒答门槛 |
| 引用有效但不支撑答案 | 优化回答与引用绑定、增加支撑校验 | 不只靠编号合法性判合格 |
| 不可回答问题经常强答 | 优化证据充分性判断与降级策略 | 不改需求分析的 F7 规则 |
| 多轮追问失败 | 优化上下文摘要/指代补全或会话材料范围 | 不无限增加历史 Token |
| 小材料表现良好、大材料超出上下文 | 评估分层检索或混合检索 | 不因技术流行直接迁移向量库 |

### 验收条件

- 明确写出本轮假设、唯一变量和预期受影响指标。
- 先保留修改前基线，再执行修改。
- 运行 DEV 回归，LOCKED 保持盲测状态。
- 输出改善、回归、不稳定结果及具体 Badcase。
- 没有证据证明改善时可以回滚，不以完成开发作为通过条件。

## Task 7｜引用定位与证据审查体验

**优先级：P1。** 可在 Task 5 基线有初步结果后开展。

- 每条可展示引用都能定位到指定文档版本。

## Task 8｜服务对话诊断模板

**优先级：P2。** 在问答基线和引用体验稳定后开展。

## 10. 技术实现与架构演进原则

### 10.1 现有路线先继续使用

当前已有 Python 标准库 Web、JSON 文件存储、DeepSeek API、n-gram 关键词检索和 pytest。下一步重点是建立质量基线，不建议在 Task 5 前一次性迁移到向量库、复杂 Agent 或新 Web 框架。

### 10.2 建议的逻辑架构

```text
Web UI
  ├── 工作台 / 资料库 / AI 问答 / 需求分析 / Dashboard
  ↓
Application Services
  ├── Project & Document Service
  ├── Cleaner Service
  ├── Analysis Workflow（现有）
  ├── Retrieval Service
  ├── Chat Service
  ├── Citation / EVD-01 Validator
  └── Evaluation Service
  ↓
Storage Layer
  ├── source.md / clean.json / paragraph_map.json
  ├── analysis_runs / citations.json / reports
  ├── conversations / messages
  └── evaluation datasets / snapshots
```

该图是逻辑分层建议，不要求立刻拆成微服务。对于当前个人项目，一个进程内的模块化单体更易调试和演示。

### 10.3 什么时候考虑混合检索

只有评测集反复证明关键词检索无法找回语义相关证据，才开展混合检索验证。候选路径可以是：

1. 在现有关键词检索上增加轻量词形归一化/同义表达。
2. 评估关键词与语义检索结果合并。
3. 在检索候选较多时评估 rerank。
4. 比较召回、引用支撑率、延迟与成本。

任何新方法必须用同一份问答评测集横向比较，且保留原有关键词基线。小材料场景不需要为了「看起来像 RAG」而引入不必要组件。

### 10.4 多轮对话的边界

- 最近 5 轮是当前实现值，不应视为永久最优配置。
- 应记录每轮实际带入的上下文和证据段落。
- 追问应允许复用历史语义，但不能把不属于当前文档范围的旧引用带入新回答。
- 当用户改变问题主题时，要防止无关历史内容污染结果。
- 后续可以考虑对历史对话做轻量摘要，但先用评测证明现有方案存在上下文长度或准确性问题。

## 11. 数据、引用与隐私保护要求

### 11.1 原始与脱敏文本分离

- `raw_text`：后端证据审计用途，限制访问。
- `clean_text`：默认用于 LLM 输入、检索、前端展示。
- `quote_model`：模型生成的转述，不作为原文证据。
- `source_excerpt`：必须由系统从选定版本的数据生成；若映射不完整，应标记 unresolved。

### 11.2 引用必须带完整身份

所有问答引用应至少能定位到：

- project_id
- document_id
- version_id
- clean_paragraph_id
- source_paragraph_ids[]
- 脱敏展示文本

仅有 `D001` 或 `P1` 不能构成完整定位，因为不同文档可以重复使用相同编号。

### 11.3 证据不足与冲突处理

回答需要区分：

- **可回答：** 材料有清晰、相关的支持证据。
- **部分可回答：** 部分事实有证据，其他部分需明确留白。
- **未提及/无法确认：** 材料没有足够依据，不能自行补齐。
- **存在矛盾：** 不同材料的说法不一致，应并列展示来源并说明未能裁定。

### 11.4 用户反馈和历史留痕

用户可以反馈答案错误，但反馈不应自动改动 GT、历史答案或 Prompt。后续若要把反馈用于优化，应经过人工审核、归类、转成新的测试用例后再进入开发集。

### 11.5 生产化边界

当前项目适合作为功能原型和个人作品集项目。在接入真实客户材料、多用户使用或对外部署前，应另行完成身份认证、项目访问隔离、密钥管理、日志中的 PII 控制、文件上传安全、备份与删除策略评估。本方案不把这些视为已经完成。

## 12. 质量指标与发布门槛

### 12.1 分清三个质量层次

1. **代码测试：** 单元测试、数据契约、异常处理和路由测试是否通过。
2. **AI 回答质量：** 问答测试集中的证据召回、答案完整、引用支撑和拒答表现。
3. **实际用户体验：** 用户是否更快完成查找、核验和整理任务。

三者互相补充，不可互相替代。

### 12.2 每次发布的最小检查清单

- 原有 68 项测试无回归；新增测试全部通过。
- 当前版本、Prompt 版本、检索配置、数据集版本及快照均有记录。
- PII 防护、引用有效性和项目范围隔离无回归。
- 已知高优先级 Badcase 未被当前变更意外引入。
- 对 AI 质量的主张由逐题证据支持，不只引用一条平均分。
- 发生回归时，能明确回滚到上一个可用版本。

### 12.3 报告格式

每次迭代报告至少包含：

- 变更目的与假设。
- 唯一变量和保持不变的条件。
- 变更前后的版本信息。
- 指标汇总及分母。
- 逐题变化和 Badcase。
- 成本、延迟和失败请求。
- 是否通过预设验收条件。
- 下一步决定：保留、回滚或继续观察。

## 13. 已知问题、风险与应对方式

| 风险 | 表现 | 应对策略 |
|---|---|---|
| 把代码测试通过误认为 AI 质量达标 | 68 项测试全绿，但回答仍可能遗漏或无依据 | 建立独立问答评测集与人工引用支撑复核 |
| 关键词检索存在词汇鸿沟 | 用户的问法与材料原文用词不同，检索不到 | 先在 DEV 集统计，再做轻量归一化或同义表达实验 |
| 只校验引用编号，不校验语义支撑 | 引用存在但不能证明对应结论 | 评测增加引用支撑率，关键题人工复核 |
| 多轮历史污染 | 当前问题误用前一轮或前一个项目的证据 | 测试切换范围、主题变化和历史引用约束 |
| 材料矛盾时擅自选边 | AI 把一方说法作为最终事实 | 加入矛盾证据测试；展示来源与差异，不自行裁决 |
| 引用完整性不足 | 只引用最显著段落，漏掉次级事实出处 | 用逐事实点引用评测定位，后续单独优化 |
| 新功能同时改动过多 | 指标变化无法归因 | 一轮一个主变量，保存独立快照和报告 |
| 技术组件过度扩张 | 提前引入向量库或 Agent，复杂度上升但效果不明 | 以错误分布和基准比较决定是否升级 |
| 产品定位分散 | 需求分析、知识库、服务诊断都想同时做 | 保持 B 端客户材料为核心领域，第二场景只做模板化验证 |
| 真实资料泄露风险 | raw_text/密钥/客户信息意外出现在前端或日志 | 默认脱敏、访问隔离、密钥不入库，并增加防泄露测试 |

## 15. 项目演示与作品集表达

### 15.1 推荐演示顺序（约 5–7 分钟）

1. **问题说明：** 客户信息散落在会议纪要、聊天记录和邮件里，人工整理慢且容易丢证据。

## 最终结论

V2 当前最重要的工作，不是继续增加更多 AI 功能，而是为已经完成的问答能力建立可衡量的质量基线。先通过 Task 5 把系统的真实表现和主要错误分布测清楚，再决定是否需要优化检索、证据组装或多轮上下文；随后完善引用交互、扩展一个场景模板，最后提升报告导出与演示体验。

**当前行动项只有一个：启动 Task 5，先盘点调用链并设计问答评测集，不修改生产问答逻辑。** 这样可以保持已有 V2 能力稳定，同时让之后每一轮优化都能够说明「为什么改、改了什么、证据是什么、是否真的改善」。
