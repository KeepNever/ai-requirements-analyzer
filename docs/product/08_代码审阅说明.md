## 2. 审阅发现的问题（按严重度）

### P1 — 已当场修复（本次审阅的直接产出）

**维度打分覆盖校验缺失。** 原代码只校验「每个维度分是 1~5 整数」，不校验「AI 是否给**每条**显性需求都打了分」。若 AI 漏打某条，该需求会静默消失在优先级表里——不报错、不进表、无人知晓。这比格式错误危险得多：格式错误会被闸门拦截，静默遗漏直接污染 F6 产出，进而污染指标⑤（优先级一致性）的评测结果。

**修复方式**：workflow.py 新增一致性校验——`priority_dimensions` 的 id 集合必须与 `explicit_needs` 的 id 集合完全一致（不多不少），不一致触发带错误反馈重试。mock 复测通过。

### P2 — 建议项（列入 M2/M3 待办，不阻塞当前）

| # | 问题 | 影响 | 计划 |
|---|---|---|---|
| 1 | mock 数据硬编码在 workflow.py（约 80 行） | 代码可读性差，mock 与真实逻辑混杂 | M2 外置为 `tests/fixtures/` JSON 文件 |
| 2 | Prompt 模板用 `.format()`，JSON 花括号需 `{{}}` 转义 | Prompt 迭代时极易漏转义导致 KeyError——M3 高频改 Prompt，这是最可能踩的坑 | M3 改用 `string.Template`（`$placeholder` 无花括号冲突） |
| 3 | 无 token 用量统计与成本熔断 | 批量跑评测时无成本可见性，异常重试无上限保护 | M2 评测流水线记录每次调用 usage，加单日成本上限熔断 |
| 4 | 用 print 而非 logging | 无级别、无落盘、不可结构化检索 | M2 换 logging，评测日志 JSONL 化 |
| 5 | 纯函数零单元测试 | cleaner/validators/scoring 是纯函数，最易测却没测 | M2 补 pytest 单测（预计覆盖三模块 90%+ 分支） |

## 4. 关键代码逐模块解释（四个核心文件）

### 4.1 prompts.py —— 规则工程的主载体

**职责**：把 05 框架的判定规则翻译成模型可执行的指令。8 个 Workflow 节点在这里映射为 2 个 LLM 调用（提取 / 分析）+ 6 个代码节点。

三个设计决策值得说：

1. **C1~C6 能力清单硬编码进 Prompt**——这是 V1 无 RAG 的降级方案（06 In/Out 表的既定决策）。清单来自 07 文档 §2 的正式版，每条带限制条款（如 C3 不支持多表关联）。硬编码的好处：判定依据唯一且版本可控，模型没有发挥空间；代价：能力清单变更时要同步改代码，M2 后由 config 加载 JSON 化。
2. **规则内嵌而非依赖模型自觉**——「推断内容混入显性需求属于严重错误」「证据不足必须输出待确认」这类硬约束直接写进 Prompt，并在 validators 用代码二次强制。双层冗余：Prompt 层防 95%，校验层拦剩下的 5%。
3. **输出 JSON 结构在 Prompt 里给全样例**——配合 DeepSeek 的 JSON mode，保证输出可直接 `json.loads`。

### 4.2 validators.py —— 错误可发现性的实体

**职责**：三道闸中最硬的一道——纯代码、零成本、无幻觉。三组校验：

| 校验组 | 防什么 | 实现 |
|---|---|---|
| schema 完整性 | 模型漏字段、输出崩坏 | 必填键逐一检查 |
| **引用真实性** | 编造依据（AI 最危险的错误形态） | `quote` 去空白后必须是所引 D 段落的子串——字符串匹配，不可能被骗过 |
| 枚举合法性 | 自由发挥 | 置信度∈{高,中,低}、匹配∈四档、分级∈{决定性,关键,普通}、维度分∈1~5 整数 |

一条被实测修正过的设计：多引用需求（如 EN3 引 D004/D005/D006）的 quote 只可能来自其中一段——首版「每段都要命中」过严，mock 自测时被自己的校验闸拦下，修正为「**所有引用编号必须存在，quote 至少命中一段**」。这个迭代过程本身就是「校验闸真的在工作」的证明。

### 4.3 scoring.py —— 无黑箱铁律的实体

**职责**：优先级加权计算。铁律是「AI 只打维度分，加权由代码执行」——模型永远不直接输出「高优先级」，输出的是 impact/urgency/coverage/signal 四个 1~5 分，权重（40/25/20/15）与阈值（3.5/2.5）在代码里，版本号 W-v0.1 显式标注为待校准假设。

这样做的两个收益：① 每个分数可回溯、可复算，产品经理可以只质疑某个维度分而不是整个结论；② 权重校准时只改代码常量并升版本号，历史评测结果的可比性不丢失。

### 4.4 workflow.py —— 链路编排与兜底的实体

**职责**：把 清洗 → 提取 → 校验 → 分析 → 校验 → 评分 → 渲染 串成一条线，落实 05 §8 的兜底三级：LLM 网络错误自动重试（llm_client 内）→ 校验失败带错误反馈重试一次（`_llm_with_gates`，错误清单回喂模型定向修正）→ 再失败流程终止并留存全部中间产物。

`_llm_with_gates` 是兜底设计的核心实现：**重试不是原样重跑，而是把校验器的具体错误喂回去**——模型知道错在哪，定向修正的成功率远高于碰运气。审查新增的「维度覆盖一致性校验」就挂在节点 2 的闸门上（见 §2 P1）。
