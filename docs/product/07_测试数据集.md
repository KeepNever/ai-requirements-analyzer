## 2. 虚构产品能力清单（被分析方：「数析云」数据分析平台）

以下清单是 05 框架第 7 节所述「V1 简化能力清单」的正式版本，硬编码进 Prompt，同时也是标准答案 F7 能力匹配的判定依据：

| 编号 | 能力 | 说明与限制 |
|---|---|---|
| C1 | 自助报表 | 拖拽式报表搭建，支持 30+ 图表类型；复杂计算字段需定制 |
| C2 | 实时看板 | 核心指标实时刷新（延迟 < 1 分钟），支持大屏投放 |
| C3 | 自然语言查询 | 自然语言转 SQL，支持常用聚合；**不支持复杂多表关联查询** |
| C4 | 智能预警 | 指标阈值预警，支持邮件/企业微信/钉钉推送；**不支持电话/短信外呼** |
| C5 | 数据集成 | 50+ 标准连接器（主流 ERP/CRM/数据库）；**私有协议需定制开发** |
| C6 | 移动端 | iOS/Android 查看报表与预警；**不支持移动端编辑报表** |
| C7 | 部署方式 | 支持公有云 SaaS 与私有化部署（客户内网/指定服务器）；信创/国产化环境需评估确认 |

## 3. 编号与引用规范

| 编号 | 含义 | 谁来生成 |
|---|---|---|
| P1、P2…… | 原始材料段落序号（案例文件内空行分段，从 1 计） | 案例撰写时固定 |
| D001、D002…… | 清洗后文本编号 | 系统清洗节点生成 |

- **标准答案（GT）一律使用 P 编号引用**——GT 在清洗之前撰写，这是刻意设计：清洗有误杀风险，GT 不能建立在清洗结果之上
- 系统输出使用 D 编号，评测时通过段落对照表换算比对

## 4. 标准答案（GT）撰写规范

1. **依据 05 框架 v1.1 的 9 字段结构**撰写，三分类判定标准直接引用 05 第 5 节
2. 显性需求每条必须附 P 编号；潜在需求必须写推断线索 + 置信度；待确认信息按「缺口 → 影响 → 追问」一条链
3. 优先级只对 GT 认定的前 3 条关键需求做四维评分，维度分取 1~5 整数，加权计算公式与分档阈值同 05 第 6 节
4. **每个案例必须单独标记「关键需求集合」**（优先级 ≥ 中的需求编号清单），作为关键需求遗漏率的固定评价基准——评测前锁定，不随 AI 输出动态调整
5. 能力匹配对照第 2 节 C 清单，允许四档结论；证据不足必须写「待确认」并说明缺什么证据
6. 每份 GT 末尾附「本案例考察点」，供评分人校准注意力
7. **事实 / 推断 / 待确认三级标注**：GT 的字段结构本身就是三级载体——F3 显性需求 = **事实层**（客户原话可查，P 引用即证据）；F4 潜在需求 = **推断层**（必须写推断线索 + 置信度）；F5 = **待确认层**（缺证据、无法定级的内容）。此分层的作用：防止评分人把 AI 的合理推断误判为「事实抽取错误」——判定标准是**看它有没有放错层**，而不是看它是不是原话。示例（引自 CASE-03 场景）：「数据不能出内网」= 事实（P7 原话）；「私有化部署是采购前提」= 高置信推断（P7 + P8 主动确认支撑）；「集团允许哪种部署形式」= 待确认（材料中无证据）
8. **潜在需求证据降级规则**：进入 F4 的推断必须满足以下之一——① 多处证据交叉指向（≥ 2 处 P 引用）；② 客户明确表达的言外之意（单处但语义明确）。仅靠评分人业务直觉「感觉客户想要」、材料中无证据支撑的判断，**降级为 F5 待确认，不得输出为潜在需求**。此规则防止 GT 自身把推测当事实，与 AI 侧的纪律对等
9. **待确认信息三级分级**：F5 每条缺口必须标注级别，写进表格「级别」列：

| 级别 | 定义 | 判定问题 | 处置要求 |
|---|---|---|---|
| **决定性** | 影响项目成立与否——不确认则方案前提崩塌 | 这个缺口不解决，这单还能不能成？ | 强制置顶，追问优先级最高，先于一切功能讨论 |
| **关键** | 影响方案设计、报价或交付周期，但不决定成单 | 不确认会不会做错方案 / 报错价？ | 必须出现在追问清单中 |
| **普通** | 影响方案细节与实施体验 | 只影响做得细不细，不影响对不对？ | 常规追问即可 |

## 5. 评分规则（防自嗨设计）

| 环节 | 规则 |
|---|---|
| 双人独立评分 | 两名评分人先不沟通，各自对照 GT 独立给 AI 输出打分 |
| 交叉复核 | 分差 > 1 的维度逐条讨论，讨论后仍分歧则记录并存档（分歧本身就是 Badcase 线索） |
| 维度一致率 | 单维度 |分差| ≤ 1 视为一致；一致率目标 ≥ 80%（初版） |
| 第三方参考 | LLM-as-judge（GLM-4.7 Flash）出参考分，不参与终审；先小样本校准一致率再启用 |
| 记录存档 | 每轮评测产出评测报告：总分 + 分维度一致率 + 分歧案例清单 |

## 6. 评测指标定义（4 核心 + 2 补充）

| 指标 | 定义 | 计算 |
|---|---|---|
| ① 需求提取准确性 | AI 提取的需求与 GT 标注的吻合程度 | F1 = 2×P×R/(P+R)，需求视为匹配要求语义等价（措辞不同不算错） |
| ② 关键需求遗漏率 | **GT 预先标注的关键需求集合**中 AI 未识别的比例；关键需求集合不根据 AI 输出的优先级动态调整 | 遗漏数 / 关键需求数（基准见各 GT 的关键需求集合标注） |
| ③ 事实与推断区分质量 | 显性需求中混入推断的污染程度 | 显性需求中无 P 引用或引用不支撑的比例 + 潜在需求缺依据的比例 |
| ④ 追问有效性 | 追问是否针对真实缺口且可回答 | 有效追问数 / 追问总数（双人评） |
| ⑤（补充）优先级一致性 | AI 档位与 GT 档位一致比例 | 一致数 / 有评分需求数 |
| ⑥（补充）能力匹配准确率 | AI 四档结论与 GT 一致比例 | 一致数 / 匹配判断数 |

**需求匹配规则（一对多 / 多对一）：**

> 允许一条 GT 需求对应 AI 多条输出（拆分）、或多条 GT 需求对应 AI 一条输出（合并），最终以**需求核心业务意图是否一致**为判断依据：
> - AI 对同一需求做了合理拆分 → 不视为额外错误，正常计入匹配
> - AI 合并后丢失了关键业务约束 → 按信息遗漏处理
>
> 此规则防止按条目数量机械计算 F1 导致评分人口径不一。

> 口径声明：5 案例为小样本，结果仅用于初步验证与 Prompt 迭代方向判断，**不得宣称普遍有效**——此声明写入评测报告模板。

**评测报告模板要素 · Badcase 错误模式分类标签：**

> 每轮评测发现的 Badcase 不做自由文本描述，一律打以下分类标签（可多选），使错误可统计、可追踪、可跨轮对比。评测时打标签，好过事后归纳。

| 标签 | 错误模式 | 典型案例 |
|---|---|---|
| BC-01 推断当事实 | 把推断写进显性需求，或显性需求缺 P 引用 | CASE-01 EN4 若无 P9 引用 |
| BC-02 引用造假 | 引用的原文不存在或不能支撑结论 | 代码级校验拦截对象 |
| BC-03 编造内容 | 编造客户没提过的需求、竞品或约束 | CASE-01 无竞品却输出竞品信号 |
| BC-04 机械频率计分 | 信号强度按提及次数统计，忽略业务影响 | CASE-05 大屏被排高优先级 |
| BC-05 忽略一票否决前提 | 急着匹配功能，漏掉部署/合规等成单前提 | CASE-03 部署约束、CASE-04 境内部署 |
| BC-06 强行归类 | 证据不足时不输出待确认，硬选匹配档 | CASE-02 店务通被判「匹配」 |
| BC-07 漏识别低频关键需求 | 关键需求仅提及一两次被漏掉或降级 | CASE-04 EN4 边界、CASE-03 EN2 |
| BC-08 显性优先级误判 | 把「客户说了」等同「重要」 | CASE-01 EN4 批次追溯 |
| BC-09 缺口识别失职 | 决定性缺口未识别，或追问空泛不可回答 | CASE-03 两处决定性缺口 |
| BC-10 建议越权 | 把优先级建议写成产品排期决策，口径越界 | F6 输出口径违规 |

> 标签与指标的对应关系：BC-01/02/03 主要污染指标③，BC-04/07/08 主要污染指标①②⑤，BC-05/06 主要污染指标⑥，BC-09 主要污染指标④。标签统计帮助定位「错在哪个节点」，比总分下降更有诊断价值。
