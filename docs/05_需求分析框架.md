## 1. 设计原则（四条铁律）

| 编号 | 原则 | 含义 |
|---|---|---|
| P1 | 显性与潜在强制分离 | 客户说过的是显性，AI 推测的是潜在，二者不得混写；潜在需求必须标注置信度 |
| P2 | 一切结论有据可查 | 显性需求必须附原文引用编号；无引用即非法输出 |
| P3 | AI 辅助判断，人做决策 | AI 负责整理、提取、推断、建议；人负责判断真伪、定优先级、做决策 |
| P4 | 无黑箱 | 评分、分类、匹配全部走可解释规则，每个输出可回答"为什么是这个值" |

## 2. 预处理层：数据清洗（两层漏斗）

### 2.1 格式清洗（纯代码，确定性 100%）

| 规则 | 做法 |
|---|---|
| 格式归一 | 去时间戳噪音、HTML 标签；微信记录统一为「说话人 + 内容」结构 |
| 去重合并 | 同一说话人连续消息合并为一条 |
| 分段编号 | 清洗后按段落编号（D001、D002……），供引用校验与回溯 |
| PII 脱敏 | 正则抓取手机号/身份证/邮箱 + 敏感词表替换；此层不过代码不得进入 LLM |

### 2.2 内容清洗（规则标记 + LLM 建议，不直接删）

| 规则 | 做法 |
|---|---|
| 无关内容过滤 | 寒暄、闲聊由关键词规则标记，LLM 复核相关性，输出过滤建议 |
| 语气归一 | 口语转写改写为中性陈述，保留原文对照 |
| 需求信号保护 | 提到功能、痛点、竞品、预算的段落打保护标，过滤层不可触碰 |

### 2.3 三条铁律

1. **标记不删除**：被过滤段落全程留痕（过滤原因可查），防误杀真需求
2. **引用链不断**：原文 → 清洗文本（D 编号）→ 分析引用，三级可回溯
3. **清洗规则进评测**：测试集埋"长得像闲聊实为需求"的陷阱句，统计需求误杀率

## 3. 分析流水线总览（V1 固定 Workflow，8 节点）

```
原始材料
  │
  ▼
[1] 预处理与清洗 ──► 清洗文本（D 编号）
  │
  ▼
[2] 信息提取 ──► 客户背景 / 业务目标 / 关键实体
  │
  ▼
[3] 需求分析 ──► 显性 / 潜在 二分类提取
  │
  ▼
[4] 优先级评分 ──► 四维打分 + 加权计算 + 原文依据
  │
  ▼
[5] 产品能力匹配 ──► 匹配 / 部分匹配 / 不支持 / 待确认
  │
  ▼
[6] 待确认信息识别 ──► 缺口 → 对判断的影响
  │
  ▼
[7] 追问生成 ──► 给销售的追问清单（对应具体缺口）
  │
  ▼
[8] 报告输出 ──► 9 字段结构化报告（草稿态）
```

| 节点 | 实现形态 | 模型 |
|---|---|---|
| 1 预处理 | 纯代码 | 无 |
| 2 信息提取 | LLM Prompt 节点 | DeepSeek V4 Flash |
| 3 需求分析 | LLM Prompt 节点 | DeepSeek V4 Flash |
| 4 优先级评分 | LLM 打维度分 + 代码加权 | DeepSeek V4 Flash |
| 5 能力匹配 | LLM Prompt 节点（内置能力清单） | DeepSeek V4 Flash |
| 6 待确认信息识别 | LLM Prompt 节点 | DeepSeek V4 Flash |
| 7 追问生成 | LLM Prompt 节点 | DeepSeek V4 Flash |
| 8 报告输出 | 模板渲染（代码） | 无 |
| 二次审批评家 | LLM 批评家节点（**实验性，见 8.5**） | DeepSeek V4 Flash |

> 架构定位：V1 为固定 Workflow，每步人写死；V1.5 在待确认信息识别处引入动态轮次；V2 追问节点 Agent 化（详见渐进式 Agent 化路线）。

## 4. 结构化报告：9 字段定义

| # | 字段 | 内容说明 | 类型 | 风险档 |
|---|---|---|---|---|
| F1 | 客户背景 | 行业、规模、角色、现状（提取） | 客观提取 | 低 |
| F2 | 业务目标 | 客户想达成什么（提取） | 客观提取 | 低 |
| F3 | 显性需求清单 | 客户明确说出的需求，每条附 D 编号引用 | 客观提取 | 低 |
| F4 | 潜在需求清单 | AI 推测的深层需求，每条带置信度 | 推断 | 中 |
| F5 | 待确认信息 | 一条链：信息缺口 → 对判断/决策的影响 → 追问建议 | 建议 | 中 |
| F6 | 优先级建议 | 四维加权总分 + 高/中/低档（**是建议，不是产品排期决策**） | 判断 | 高 |
| F7 | 产品能力匹配 | 每条需求对照能力清单的匹配结论 | 判断 | 高 |
| F8 | 竞品信号 | 材料中提到的竞品及态度（提取） | 客观提取 | 低 |
| F9 | 综合摘要 | 面向产品经理的一屏结论：已知事实、主要风险、待确认项 | 综合 | 中 |

> 风险档判定依据四维标准（决策影响 / 错误可发现性 / AI 可靠性 / 错误可逆性），两维及以上达高即入高风险档，详见第 8 节。
>
> 口径说明：客户需求的重要程度 ≠ 产品团队的最终开发优先级。排期还受产品战略、开发成本、技术风险、商业价值等影响。V1 只输出需求层面的优先级建议，报告中原样标注此边界。

## 5. 显性 / 潜在 / 待确认三分类规则

| 类别 | 判定标准 | 输出要求 |
|---|---|---|
| 显性需求 | 客户原话中明确表达的诉求，可指向具体语句 | 必须附 D 编号引用；一条引用支撑一条需求 |
| 潜在需求 | 从背景、目标、抱怨中推断出的未明说需求 | 必须写推断依据（引用哪些线索）+ 置信度（高/中/低） |
| 待确认信息 | 影响判断但材料未覆盖的背景、约束或需求信息 | 按「缺口 → 影响 → 追问」一条链输出，不拆成两个重复字段 |

**硬约束（进 Prompt + 代码双重校验）：**
- 显性需求无 D 编号引用 → 非法输出，触发重生成
- 推断性措辞（"可能""或许""大概率"）出现在显性需求中 → 批评家节点拦截（若实验保留）
- 潜在需求缺置信度 → schema 校验失败，重试

## 6. 优先级评分模型

### 6.1 四维权重表（V1 待校准假设，非行业标准）

| 维度 | 权重 | 定义 | 评分锚点（1 / 3 / 5 分） |
|---|---|---|---|
| 业务影响 | 40% | 该需求对客户核心业务目标的影响程度 | 1 锦上添花 / 3 明显提效 / 5 不做就丢单 |
| 紧迫性 | 25% | 客户期望的时间窗口 | 1 无期限 / 3 季度内 / 5 明确 deadline |
| 用户覆盖 | 20% | 受益用户在客户组织中的占比 | 1 个别人 / 3 某个部门 / 5 全员 |
| 需求信号强度 | 15% | 综合信号：重复提及 + 客户是否主动强调 + 是否与业务目标直接相关（**非机械统计次数**） | 1 单次顺带提及 / 3 多次提及或主动强调 / 5 反复强调且与业务目标直接相关 |

### 6.2 计算与分档

- 总分 = Σ(维度分 × 权重)，满分 5.0
- 高：≥ 3.5 ｜ 中：2.5 ~ 3.4 ｜ 低：< 2.5
- AI 只输出四个维度分及各维原文依据，**加权计算由代码执行**（P4 无黑箱）
- 每个维度分必须附一句原文依据，缺依据重生成

### 6.3 校准计划

1. V1 评测阶段：双人独立给测试案例需求定优先级 → 与模型分对比 → 系统性偏差则调权重或锚点
2. 校准结论记入评测报告，权重表标注版本号（如 W-v0.1 → W-v1.0）

### 6.4 输出口径

- 报告中该字段命名为「优先级**建议**」，并在输出中原样标注：此为需求层面的建议，不代表产品排期决策（排期还受产品战略、开发成本、技术风险、商业价值影响）

## 7. 产品能力匹配（V1 降级方案）

- V1 不建 RAG 知识库，能力清单以**简化版硬编码进 Prompt**：5~8 个功能的一句话描述（须写明已有能力及其限制，防止模型仅凭语义相似就判"匹配"）
- 匹配判定四档：**匹配 / 部分匹配（需定制或变通）/ 不支持 / 待确认**
- **待确认档使用规则**：能力描述不足或证据不充分时必须输出"待确认"，不得强行归入其他三档
- 输出要求：每条匹配结论附理由（同时引用需求原文 D 编号 + 能力清单条目）
- 硬约束：「不支持」与「待确认」均视为高风险输出，AI 只出建议，强制人工确认（防止对客户错误承诺）

## 8. 审核分层设计（三道闸 + 三档审核）

### 8.1 第一层：AI 自审（输出前，机器拦机器）

| 闸门 | 机制 | 防什么 | 实施阶段 |
|---|---|---|---|
| 输出约束 | 显性需求必须带 D 编号引用，缺引用即非法 | 编造客户没说过的话 | V1 必做 |
| 代码级校验 | 程序验证引用片段真实存在于清洗文本 + JSON schema 必填检查 | 引用造假、格式崩坏（纯代码，最硬） | V1 必做 |
| 二次审批评家 | 批评家角色审"是否把推断写成事实、是否编造"，高危问题触发重跑 | 模型自我倾向 | **实验性（见 8.5）** |

### 8.2 第二层：人工审核（输出后，按风险分级）

| 风险档 | 字段 | 审核策略 |
|---|---|---|
| 高风险 | F6 优先级建议、F7 能力匹配（尤其"不支持"与"待确认"）、潜在需求置信度 | 强制人工确认，AI 只出建议 |
| 中风险 | F4 潜在需求内容、F5 待确认信息 | 默认采纳，产品经理可改可驳 |
| 低风险 | F1/F2/F3/F8 客观提取 | 自动通过，标记异常才看 |

### 8.3 风险分档四维判断标准

| 维度 | 判断问题 |
|---|---|
| ① 决策影响 | 字段错了是否直接导致错误决策？ |
| ② 错误可发现性 | 只对照原文能否一眼核对出错误？ |
| ③ AI 可靠性 | 任务是提取（有锚点、稳）还是推断（无锚点、易漂移）？ |
| ④ 错误可逆性 | 改一行字即可，还是会传导为外部动作？ |

**归档规则：两维及以上达"高"即入高风险档。** 可解释、可复算。

### 8.4 修正留痕三件套

判断类字段可修正，必须记录：AI 原判断 / 人工判断 / 修改原因。此数据用于 Badcase 归档与 Prompt 优化（修正数据回流，非自动学习）。

### 8.5 可靠性机制实施清单（分层管理）

| 层级 | 机制 | 说明 |
|---|---|---|
| V1 必做 | 结构化输出校验（schema）、显性需求引用校验、关键信息缺失提示、优先级代码计算、高风险字段人工确认 | 支撑主流程可信的最小集 |
| V1 实验性 | 二次审批评家（批评家节点） | **对照实验设计**：第一轮评测不带批评家，量编造率基线；第二轮加上，量差值。11 案例上未拦到额外问题即砍掉——留不留由评测数据决定 |
| 后续增强 | 完整风险分层策略、复杂状态流转、多轮材料复核、PII 全量脱敏流水线 | 依据 V1 测试结果与用户反馈决定是否进入后续版本 |

## 9. 需求状态流转（V1 雏形）

```
新发现 ──► 待确认 ──► 已确认
              │
              └──► 已否定
```

| 规则 | 说明 |
|---|---|
| 流转权限 | 仅产品经理（R2）可流转状态 |
| 销售与售前 | 只读，可发起追问（自动流向销售） |
| V2 演进 | 多轮材料演化时，新材料触发状态复核（AI 提议流转，人工审批） |
