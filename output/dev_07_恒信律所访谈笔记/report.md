## F1 客户背景

- 律所规模 45 名执业律师，分 6 个团队（D001）
- 行政与 IT 均无专职人员，由行政主管林姐兼管系统事务（D001）
- 律师办案进度散落在各自电脑的文件夹和 Excel 里，合伙人想看全所案件状态要挨个微信问团队长（D002）
- 案件管理用的是所里十年前找外包做的小系统，B/S 架构，数据库 SQL Server，没有现成接口，外包公司已经联系不上了（D004）

## F2 业务目标

- 让合伙人能掌握全所案件状态，不再依赖逐个微信询问团队长（D002）
- 支撑张律师每周一下午合伙人会议前的数据准备（D003）
- 提升行政出账单与工时统计的准确性与效率，减少合伙人退回重做（D005）
- 在数据不出所内的前提下实现数据查询与统计（D008）

## F7 能力匹配

| 对象 | 结论 | 依据 |
|---|---|---|
| EN1 看板展示各团队在手案件数、本月创收、回款情况 | 部分匹配 | C2 实时看板支持核心指标实时刷新与大屏投放，可承载看板展示；但数据来源依赖老系统（D004 无接口），需先解决数据集成（C5 私有协议需定制开发），故为部分匹配 |
| EN2 看板需在每周一下午合伙人会议前可用 | 匹配 | C2 实时看板延迟 < 1 分钟，满足会议前获取最新数据的时间要求 |

| EN4 用大白话直接向系统提问要数 | 部分匹配 | C3 自然语言查询支持自然语言转 SQL 与常用聚合，可覆盖「上个月张律师团队的回款是多少」这类查询；但 C3 明确不支持复杂多表关联查询，若涉及跨表则受限 |

| EN6 查询结果必须准确 | 待确认 | 能力清单未对数据准确性作明确说明，准确性取决于数据集成质量与计算逻辑，需结合老系统数据源情况确认 |
| EN7 案件数据绝对不能出所内 | 待确认 | 能力清单未说明部署方式（本地化/云端），C1~C6 均未提及部署架构，无法判定是否支持数据不出所内的本地化部署 |
