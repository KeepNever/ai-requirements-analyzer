## F1 客户背景

- 律所规模 45 名执业律师，分 6 个团队（D001）。
- 行政与 IT 均无专职人员，由行政主管林姐兼管系统事务（D001）。
- 律师办案进度散落在各自电脑的文件夹和 Excel 里，合伙人需挨个微信问团队长才能了解全所案件状态（D002）。
- 案件管理使用十年前外包开发的小系统，B/S 架构、SQL Server 数据库，无现成接口，外包公司已失联（D004）。
- 每月客户账单与律师工时统计需从老系统导出后手工核对，耗时两天且常出错被退回（D005）。
- 数据安全要求严格：案件数据不能出所内，云端方案已被合伙人会否决，客户均签有保密协议（D008）。
- 今年信息化预算 8 万，超过 10 万需重新开合伙人会（D009）。

## F2 业务目标

- 让合伙人能集中查看全所及各团队案件状态，替代挨个微信询问团队长的方式（D002）。
- 在每周一下午合伙人会议前获得各团队在手案件数、本月创收、回款情况（D003）。
- 提升月度账单与工时统计的准确性和效率，减少手工核对与返工（D005、D007）。
- 以自然语言和交叉维度方式便捷取数，降低对专职 IT 人员的依赖（D006）。
- 在数据不出所内的前提下实现信息化，满足客户保密协议要求（D008）。
- 控制投入在预算范围内，工具需能省时间省钱（D009）。

## F7 能力匹配

| 对象 | 结论 | 依据 |
|---|---|---|
| EN1 团队案件数/创收/回款看板 | 匹配 | C2 实时看板支持核心指标实时刷新与大屏投放，可承载每周合伙人会议前的指标展示；数据来源依赖 C5 数据集成对接老系统 SQL Server（属标准数据库连接器范围），实施工作量与接口风险写入实施评估，不因此降档 |
| EN2 月度客户账单与工时统计自动生成 | 部分匹配 | C1 自助报表可覆盖工时统计类内部报表的搭建；但 C1 明文说明对外正式账单/对账单等格式属定制输出、非标准报表能力，账单正式格式部分存在缺口，需定制开发 |
| EN3 自然语言取数（如查某团队某月回款） | 匹配 | C3 自然语言转 SQL 支持常用聚合，单团队单月回款查询属典型聚合场景，在能力范围内 |
| EN4 按客户/案件类型/月份交叉组合查询 | 待确认 | C3 明文不支持复杂多表关联查询，而按客户、案件类型、月份组合查询是否构成多表关联取决于数据模型设计，材料未提供数据结构证据，无法判定由 C3 还是 C1 拖拽报表承载，缺少关键证据 |
| EN5 查询结果准确性 | 匹配 | 准确性属数据质量与实施保障范畴，C1/C2/C3 均以数据源为基础，通过集成与口径定义保障；无清单级排除项 |
| EN6 数据不出所内（私有化部署） | 匹配 | C7 支持私有化部署（客户内网/指定服务器），可满足数据不出所内要求；需注意 C7 提示信创/国产化环境需评估确认，材料未提及信创要求 |
| IN1 老系统数据集成 | 匹配 | C5 提供 50+ 标准连接器含主流数据库，SQL Server 属标准连接范围；老系统无现成接口属实施对接工作，按规则保持匹配，接口缺失与外包失联带来的工作量风险写入实施评估 |
| IN4 对外正式账单格式输出 | 部分匹配 | 同 EN2，C1 明文将对外正式账单/对账单列为定制输出，标准报表能力不覆盖正式账单格式，需定制 |
